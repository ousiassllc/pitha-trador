### 4.10 Scheduler / Worker

- FR-SCHED-1: 以下の6 Queueで非同期処理する: market-data, feature-calc, jev-scout, jev-trader, outcome-labeling, analytics。特徴量の算出・永続化は`market-data`ジョブ内で原子的に実行し、`feature-calc`キューは互換用の空ハンドラ（成功するだけで処理は行わない）として残し、フルスキャンは`feature-calc`ジョブをenqueueしない（4,000銘柄で毎分4,000件の空ジョブを積まないため。以前のバージョンが残した未処理の`feature-calc`ジョブをこのハンドラが消化する）。フルスキャンの`market-data`ジョブは全銘柄分を1トランザクションでenqueueする。`jev-scout`は候補更新サイクルおよびイベント再評価（FR-SCAN-1）から、`jev-trader`は`jev-scout`ジョブから、それぞれenqueueされる。`outcome-labeling`は毎分のcron（`@every 1m`）が判定水平線（5/10/15分。FR-CAL-5）を経過したJev判断を拾ってenqueueし、`analytics`は平日15:40 JSTのSol/Opus自己改善バッチ（FR-SELFIMPROVE-1）専用である（いずれも約定・Exitを契機にはしない）。Risk判定とPaper発注は独立Queueを持たず、`jev-trader`ジョブ内でPolicy Engineの直後に同期実行する（Risk Engineの承認なしにExecutionへ到達しない不変条件を、ジョブ間の非同期境界で崩さないため）
- FR-SCHED-2: （`scan.full_scan_enabled: true`を明示したときだけ。既定はオフでFR-SCHED-7・FR-SCHED-9のランキング監視に置き換わる）60秒周期でuniverse snapshot取得（`instruments`の有効な全銘柄の板をkabuステーションAPIから取得）・特徴量算出・screen・Jev Scout enqueueを行う。フルスキャンは`kind`を区別せず、`stock`に加えて市場コンテキスト特徴量（FR-FE-4）の算出に必要な`market_index`/`sector_index`にも同じ`market-data`ジョブを投入し、板（PUSH購読が無いためREST）取得→特徴量算出→スナップショット保存を行う。一方、PUSH購読（PushFeed）と候補更新（Fast Screener→Jev Scout）は`stock`のみを対象とする。板・銘柄情報・銘柄登録のRESTはプロセス全体で公式10件/秒未満（既定`scan.kabu_info_api_max_per_second`=8）に制限する。60秒でREST板を取れるのは最大約480銘柄（＋PUSH最大40。API登録上限50のうちREST回転用に10件を空ける）で、残りは同一サイクルの続きとして消化し次の60秒tickは投入をスキップする（`non-functional.md` §2.3、issue #514）。`instruments`は起動時に銘柄マスタCSV（`environment/setup.md`「銘柄マスタの投入」）から`internal/bootstrap`が冪等にupsertする（既存行の`is_active`は変更しない）。CSVが無くDBも空の場合はスキャン対象が0件になるためエラーログに記録する
  - 制約（issue #693/#694/#696）: 全件RESTは1周が約8分かかるため各銘柄の足は約8分に1回しか書かれず、Feature Engineの窓の基準バーの許容（FR-FE-6）を超える。そのため`scan.full_scan_enabled: true`では履歴ベース特徴量（`return_1m/3m/5m`・`volume_*`・`turnover_*`・`market_return_*`・`sector_return_5m`・`market_breadth`等）が常に欠損となり、Fast Screenerの通過が0件のまま候補が空になる（詳細はFR-SCHED-7）
- FR-SCHED-3: 15〜30秒周期でshortlist銘柄を再評価する
- FR-SCHED-4: 5〜15秒周期で保有ポジションのExit条件を評価する（`scan.held_position_interval_seconds_min/max` の範囲でランダムに揺らした周期で、保有銘柄のみブローカーのストリームフィード（`broker.StreamFeed.Latest`。既定のkabuアダプタでは`pushfeed.Feed.Latest`）で最新のQuote（板）を得て（保有・注文中は監視リストの固定枠＝PUSH登録済みのため、直近30秒以内のPUSH板があればRESTを呼ばず、無いときだけREST `/board`で補う。issue #709）`execution.Engine.OnSnapshot` を呼ぶ。立会時間外は行わない）
- FR-SCHED-5: Workerはポーリングごとに期限到来済みのjobを空になるまで連続処理する（1ポーリング1jobに制限しない）
- FR-SCHED-6: ハンドラ・cronトリガー・バックグラウンドgoroutineがpanicしてもプロセスを落とさず、該当jobは`failed`（`last_error`に`handler panic: ...`）として記録し、スタックトレースをログに出力する。常駐goroutine（候補更新・保有監視・PushFeed・News Ingest・トークン再発行）は`internal/safego`で1サイクル単位にpanicを回復し、ループを継続する（保有監視は銘柄単位でも回復し、1銘柄のpanicで後続ポジションのExit評価を止めない）
- FR-SCHED-7: 全銘柄RESTスキャン（FR-SCHED-2の60秒ごとの`market-data`全件投入）は`config/strategy.yaml`の`scan.full_scan_enabled`でオン/オフできる。**既定はオフ**（同梱既定は`false`、キー省略時も`false`。明示的に`true`にしたときだけ全件投入する。#651の方針転換・#652）。オフのときSchedulerはフルスキャンのcronトリガーを登録せず（起動時に`scheduler: full scan off (scan.full_scan_enabled is not true)`をINFOで1回記録）、`EnqueueFullScan`も何も投入しないため、`market_index`/`sector_index`を含む`market-data`の全件投入は行われない。代わりにFR-SCHED-9のランキング監視が決めた銘柄と、市場コンテキスト（FR-FE-4）の算出に必要な有効な`market_index`（全件）・`sector_index`（監視銘柄の`sector`と一致するもの）だけを投入する。候補更新・イベント再評価・保有監視・PUSH購読など他のトリガーには影響しない。オフ中は上記以外の`market-data`ジョブが走らないため、監視銘柄・上記の指数行以外の板・特徴量・スナップショットは更新されない。指数行は更新されるので`market_return_1m/5m`・`sector_return_5m`・Risk Engineの`market_adverse_to_direction`ゲート（FR-RISK-1）は既定でも機能するが、`market_breadth`（FR-FE-4）は全アクティブ株式ではなく、市況コンテキストの許容年齢（`domain.MarketContextMaxAge`＝3分）以内に更新された監視銘柄（最大45）の上昇・下落比になる（全体の地合いを表さない）。環境変数・DB `runtime_settings`による上書きはない（`strategy.yaml`のみ）
  - **全件スキャンの制約（issue #693/#694/#696）**: `true`では各銘柄（指数行を含む）の足が全件RESTの1周（約8分）に1回しか書かれず、窓の基準バーの許容（`max(窓幅/2, 90秒)`。FR-FE-6）を満たせないため、`return_1m/3m/5m`・`volume_*`・`volume_ratio_*`・`turnover_1m/5m`・`realized_vol_*`・`market_return_1m/5m`・`sector_return_5m`・`market_breadth`が全銘柄で常に欠損となり、Fast Screenerは全銘柄を欠損で除外して**候補が空のまま**になる（Jev Scout・Trader・Paper Entryは動かない）。Risk Engineの`market_adverse_to_direction`ゲート（FR-RISK-1）も`market_return_5m`が欠損のため素通りとなり**機能しない**。`scan.full_scan_max_snapshot_age_seconds`（620秒。FR-FE-4・FR-SCAN-5）は最新の足の鮮度判定（`stale_snapshot`）を緩めるだけで、この欠損は解消しない。基準バーの許容を広げると8分間の変化を「N分モメンタム」と誤認するため、許容は広げない。サポートする運用は既定のランキング監視（FR-SCHED-9）であり、全件スキャンを明示的にオンにした場合は起動時にこの制約を説明するWARNログ（`scheduler: full scan on (scan.full_scan_enabled: true): bars arrive about every 8 minutes, …`）を1回記録する
- FR-SCHED-8: kabu `GET /ranking`（詳細ランキング）の計測ループを`scan.ranking_measure`でオプトイン有効化できる（既定`enabled: false`）。有効時は`interval_seconds`（既定60）ごとに、`types`（種別1〜15。既定1〜7＝値上がり率〜売買代金急増）×`exchanges`（`ALL`/`T`/`TP`/`TS`/`TG`/`M`/`FK`/`S`。既定`T`/`TP`/`TS`/`TG`）の全組み合わせを取得する。既定では立会時間内のみ取得し、`include_outside_session: true`で立会時間外（8:55〜9:10のデータ復帰時間の計測など）も取得する。1リクエストごとに構造化ログ`rankingmeasure: ranking measured`へ`type`・`exchange`・`duration_ms`・`ok`・成功時の`result_count`（件数）・`duplicate_ranks`（同順位の重複行数）・`current_price_time`（行の`CurrentPriceTime`の最大値`HH:mm`）・失敗時の`http_status`・`kabu_code`・`rate_limited`・`error`**だけ**を記録する。取得した価格・出来高・銘柄コード・銘柄名などランキングの中身は、DB保存はもちろんログ出力もしない（`marketdata.Client.MeasureRanking`がレスポンスを件数と時刻へ縮約し、価格は最初からデコードしない。取得した時価の保存はkabuの利用規約上許容されない: kabusapi#1343）。呼び出しは情報APIのプロセス全体レート制限（`scan.kabu_info_api_max_per_second`）を共有し、1サイクルの呼び出し数は`types`×`exchanges`件、1件の失敗・panicは他の組み合わせを止めない。`types`・`exchanges`が範囲外の値のときは起動時の検証でエラーにする。実機での計測（#652の表1〜9）と段階1の設計値決定は運用者が行う
- FR-SCHED-9: ランキング監視（`internal/bootstrap/rankingwatch`）。`scan.full_scan_enabled`が`true`でない限り（既定）、監視銘柄は全銘柄REST走査ではなくブローカーの候補ソース（`broker.CandidateSource.Candidates`。既定＝kabuアダプタでは`GET /ranking`の種別1〜7＝値上がり率・値下がり率・売買高・売買代金・TICK回数・売買高急増・売買代金急増を市場`T`で取得し、順位ごとに交互に並べたもの。種別・市場はkabuアダプタ内の定義）の毎分（60秒）取得で決める。ランキングを持たないブローカー（`broker.Capabilities.Ranking`が偽）ではこの監視は起動しない。7種別を順位ごとに交互に並べ（各種別の1位、2位…）、`instruments`の有効な`stock`に含まれる銘柄だけを候補とする。監視リスト（＝ブローカーのストリーム登録銘柄。kabuではPUSH登録銘柄）は**最大45銘柄**（`broker.Capabilities.MaxStreamSymbols`。kabuアダプタでは、API登録銘柄リスト50件のうち5件をRESTの`/board`・`/symbol`用に空けた値）で、①保有ポジション・注文中（`PENDING`）の銘柄は固定枠（ランキングに無くても外れず、`min_hold`・入れ替え上限にも優先する）、②入れ替えは1サイクル（1分）あたり**最大5銘柄**（空き枠への追加は上限なし）、③ランキングから入れた銘柄は**最低5分**残す。監視リストは(a)`PUT /register`（`pushfeed.Feed.SetWatch`。外れた銘柄は`PUT /unregister`で枠を空ける。PUSH再接続時は直近の監視リストを再登録する）、(b)監視銘柄ごとの`market-data`ジョブ投入（`Scheduler.EnqueueMarketData`。立会時間内・前サイクル未完了なら投入しない。市場コンテキスト算出用の有効な`market_index`全件と、監視銘柄の`sector`に一致する`sector_index`も毎サイクル同じジョブで投入する。PUSH登録・候補の対象には含めない。#670）、(c)Fast Screenerの対象（`candidates.Refresher.Watch`）に使う。このためスキャン状況パネルのファネル「ユニバース」と「スキャン対象を見る」の一覧（FR-SCAN-3/4）の母集団は監視銘柄になり、全銘柄（最大約4,000）は`scan.full_scan_enabled: true`のときだけである。立会時間外（昼休みを含む）はランキングを取得せず、(a)PUSH登録・(b)`market-data`投入は保有・注文中の銘柄だけに停止するが、(c)の候補リスト・スキャン対象の一覧は直前の立会時間内サイクルの監視リスト（＋保有・注文中）を保存済みデータで評価して表示し続ける（最低保持時間の起点も保たれ、立会再開時はその状態からランキング取得を再開する。FR-SCAN-7。ただし立会中に最新の足がSettingsの`scan.snapshot_max_age_seconds`（既定`domain.DefaultMaxSnapshotAge`＝20秒。FR-FE-7）より古い銘柄（`scan.full_scan_enabled: true`では`scan.full_scan_max_snapshot_age_seconds`超。FR-SCAN-7）は、保持・新規監視入りを問わず`stale_snapshot`で除外してJev Scoutへ投入せず、新しい足が書かれてから評価する。Jev Scout/Trader（`HandleJob`）も古い最新足のジョブは再試行なしでスキップし、Paper Entryは壁時計でも立会中でなければ見送る。issue #685）。プロセス再起動直後の立会時間外は直前のリストが無いため保有・注文中の銘柄だけになる。**ランキングが空（平日7:53頃〜9:00過ぎはkabuの仕様で空）または取得に失敗（HTTP/kabuエラー・トークン無し・流量超過・デコードエラー・panic。7種別のうち1つでも失敗したサイクルは全体を失敗扱い）したときは、ランキング由来の候補は0件**になる: 前サイクルのランキング銘柄を古いまま残さず、保有・注文中の固定枠だけの監視リスト（なければ空）を公開・登録・投入し、Scanner Dashboardの候補も空になる。プロセスもジョブも停止・異常終了せず、次のサイクル（1分後）で自動的に復帰する。ログは`rankingwatch: watch list updated`（毎分）・`ranking is empty`・`ranking failed`・`ranking recovered`で、件数・`duration_ms`・kabuエラーコードだけを出し、失敗・空の繰り返しは10分に1回に間引く。ランキングの価格・出来高・銘柄名はデコードすらせず（`marketdata.Client.RankingSymbols`は銘柄コードだけを返す）、銘柄コードもメモリ上の選定にのみ使いログにもDBにも出さない（kabu利用規約: kabusapi#1343、#652）。**対象外**: #651の寄り前監視リスト（J-Quants Lightの前日データで8:59にPUSH登録）はデータソース・認証情報が無いため未実装。#652の実機計測9項目も未実施

### 4.11 バックテスト

Paper Trading開始前に最低限以下を検証する。

- FR-BT-1: 取引回数、勝率、平均利益、平均損失、Profit Factor、Expectancy、Max Drawdown、スリッページ込みPnL、手数料込みPnLを算出する
- FR-BT-2: Training/Calibration → Validation → Forward periodのWalk Forwardを繰り返す（全期間一括最適化しない）
- FR-BT-3: 特徴量は判定時点までのデータのみで生成する（look-ahead防止）
- FR-BT-4（再現範囲と残る差。issue #775）: バックテストおよびシャドーバックテスト（FR-SELFIMPROVE-4）は、記録済みの`market_snapshots`・`jev_decisions`（Jev Trader判断）・`metalabel_models`から、ライブと同じ判断フロー（Fast Screener → Jev Scout → Jev Trader → ハードガード → メタラベリング → Risk Engine → Exit）を再生して取引を再現する。ライブ運用の結果とは完全には一致せず、Expectancy・Max Drawdownは下記「残る差」を前提とした比較値である。新規の永続化は無い（再現結果は読み出し時に既存テーブルから計算する）
  - 記録の再生と再計算の区別: **記録の再生**は、Fast Screener／Jev Scoutの結果（銘柄が候補になったことは`jev_decisions`にJev Trader判断が存在することで表れる。スクリーニング・Scoutは再実行しない）、Jev Trader判断そのもの（`response_json`。Jevは再呼び出ししない）、足ごとの特徴量（`market_snapshots`）、保存済みメタモデル（`metalabel_models`）。**再計算**は、ハードガード（スプレッド・流動性・特別気配・値幅制限・貸借・entry_quality・continuation・toxic_flow・liquidity_stressed。`policy.InputFromSnapshot`と同一の決定木）、メタモデルの推論とtake/skip（`policy.Engine.DecideReplay`＝ライブ`Evaluate`と同じ決定木）、Risk Engine（`backtest/simrisk`）、約定（`fillmodel`）、全Exit条件（`execution/exitcond.Evaluate`＝ライブ`EvaluateExit`と同一関数）
  - エントリー可否（メタモデル。FR-POLICY-6）: ライブと同じく、ハードガードを通ったJev候補を、メタモデルの較正後EVが0超かつ最低EV超のときだけ取る。採点に使うのは判断時刻より前（`trained_at`が判断時刻より厳密に前）に学習済みで`status=active`だったモデルのうち最新の1つだけで（ウォークフォワード。再現中に学習・保存はしない。`rejected`は一度も有効でなかったものとして使わない）、判断より後に学習したモデルは決して使わない。**その時点で有効なモデルが1つも無い期間はエントリー0件**（ライブの`no_active_model`見送りと同じ。`meta_skip`）。最新モデルが特徴量レイアウト不一致等で使えない場合も古いモデルへ戻らず見送る（ライブの`meta_model_unavailable`と同じ）。モデル入力のうち`tdnet_score`は、判断に記録された`news_context`から学習時と同じ規則で再構成し、読めない・欠ける特徴量があればモデルは見送る（推測で補わない）。旧`confidence >= policy.*.min_probability`の規則は既定では使わない（`RunConfig.Entry`を`EntryLegacyConfidence`と明示したときだけの比較専用モード。`backtest.CompareEntryRules`が同じ履歴を新旧の規則で再生して差を返す。既定経路が旧規則を使わないことはテストで保証する）
  - Risk Engine（§4.7）: `RunConfig.Risk`の`backtest/simrisk`がライブの`risk.Engine.Check`と同じ順序・理由文言で評価する（Kill Switch状態 → 損失後クールダウン → max_open_positions → 同方向上限 → 総エクスポージャ・銘柄別エクスポージャ → 日次損失上限 → 連敗上限 → スプレッド → 市場逆行 → サイジング）。純粋ルール（`risk/correlation`・`risk/sizing`）はライブと共有し、状態（保有数・方向別数・エクスポージャ・当日損益・連敗・最終損失時刻）は再生した取引から作る。複数銘柄は時刻順に1つのポートフォリオとして再生するため上限は銘柄をまたいで効く（シャドーバックテストも全銘柄を1ポートフォリオで再生する）。サイジングは`sizing.Quantity`（数量はリスク判定とエクスポージャ計算にのみ使い、集計する損益は価格リターン（%）のまま）。メタラベルの`SizeFraction`は数量に使わない（ライブと同じ。#781）。銘柄ごとの損失後クールダウン（`CooldownAfterLossMinutes`）も再現する。**再現できない状態の扱い**: 運用者の一時停止・手動Kill Switch・市場データ/Jev API/ブローカー障害由来のKill Switch・UIハートビートは記録が無いため常に非発動とみなす。日次損失上限・連敗上限のKill Switchは再生した損益から導けるので再現し（ライブ同様、発動後はその営業日の残りのエントリーを拒否）、ライブでは運用者の手動再開までラッチされるが、再現では翌営業日（JST）の開始時に運用者が再開したものとして連敗カウントとクールダウンの起点を戻す。FR-RISK-8の日次エントリー停止（円建て損失上限・利益確定・取引回数）は再現しない。`RunConfig.Risk`が空のときはRisk Engineなしで再生する（比較用の明示モード。`backtestsource`は常に設定する）
  - Exit条件（FR-EXIT-1/2）: ライブと同じ優先順で全条件を評価する（Stop Loss → Take Profit → Trailing Stop → Jev方向反転 → continuation_probability低下 → VWAP逆クロス → 最大保有時間 → 引け前強制決済。`exit_reason`はPaperの`positions.exit_reason`と同じ名前で記録する）。値は`execution.Config`と同一。Trailing Stopの基準は建玉後の足の最良価格、VWAP逆クロスの基準は直前の評価時の価格/VWAP、Jev判断は足の時刻以前の最新の記録（無ければJev由来の2条件のみ無効。FR-EXIT-3）、continuationの閾値はmin(Exit設定, 現在の入口閾値)。引け前強制決済は大引け（`marketcalendar`）の`ForceFlatBeforeMarketCloseMinutes`前から発動し、その時刻以降は新規エントリーも行わない。約定できない足（昼休み・立会時間外）で発動したExitは次の約定可能な足で再評価する。データ末尾まで条件が成立しない場合は約定できた最後の足で`data_ended`として決済する（Paperには対応する理由が無い）
  - 再現性の検証（Paperとの突き合わせ）: `backtestsource.Source.VerifyReproducibility`が、指定期間を同じ設定で再生した結果と、同期間にPaperが実際に建てたポジション（`positions`）を比較し、エントリーの件数・銘柄・時刻（許容差内で最も近いものを1対1で対応付け）の一致率、方向の一致数、決済済みの対応分の`exit_reason`の一致率と分布、両者の件数・勝率・Expectancy・Max Drawdownを数値で返す（`backtest/parity`。保存はしない）。一致率には暫定の下限（`parity.Provisional`: エントリー一致率0.5以上、`exit_reason`一致率0.5以上、時刻の許容差2分）があり、下回ると判定は「不合格」で`Report.Err()`がエラーを返す。Paperのエントリーが期間内に1件も無い場合は判定を「データ無し」とし、失敗にはしない。暫定下限はPaperの実績が無く較正できないため緩い仮置きで、実績の一致率が得られた時点で引き上げる。運用者向けの実行導線は読み取り専用のCLI`cmd/backtestverify`（`go run ./cmd/backtestverify -db <Paper運用のDB> [-from YYYY-MM-DD -to YYYY-MM-DD]`）。`-from`/`-to`はJSTの日付（両端を含む）で、どちらも省略すると自己改善のシャドーバックテストと同じ直近30営業日（FR-SELFIMPROVE-4。東証営業日）、片方だけの指定はエラー。DBは`mode=ro`で開きマイグレーションも保存もしない（`sqlitedb.OpenReadOnly`。WALのDBでは空の`-wal`/`-shm`が隣に作られる）。`-db`省略時は`PITHA_DB_PATH`、無ければアプリと同じ利用者別の`pitha.db`で、設定は`PITHA_STRATEGY_PATH`/`PITHA_RISK_PATH`でアプリと同じく選ぶ。`parity.Report.String()`を表示し、終了コードは合格・データ無しが0、不合格（`Report.Err()`。理由はstderr）が1、フラグ不正・DB/設定/再生の失敗が2。しきい値（`parity.Provisional`）を変えるフラグは無い。検証期間の選び方（実績が十分にある期間か）と一致率の評価は運用者の判断で、この手順は数値を出して下限割れを検知するだけ
  - Jev判断の消費: 1件のJev Trader判断は高々1回のPolicy評価（＝最大1エントリー）にのみ使う。評価済み（エントリー有無を問わない）の判断、およびポジション保有中に記録された判断は、Exit後に再利用せず、新しい判断が記録されるまでは判断なし（`ReasonMissingData`）として扱う。ライブの「判断1件→最大1シグナル」に合わせるための簡略化であり、判断の鮮度上限（失効時間）は設けない
  - 保有足の無いエントリー: エントリー足の次に約定できる足が無い（データ終端）場合は約定・保有できないものとして取引に計上しない（entry==exitの0リターン取引を作らない）。その判断は消費済みとなる。次の足が最大保有時間を超えている（前場引け・大引け・欠測の跨ぎ）場合は、ライブの`OnSnapshot`と同じくその足で最大保有時間のExitとして決済する
  - エントリー可否の入力: Policy Engineへ渡す入力は、ライブ（Jev Traderジョブ）と同じ`policy.InputFromSnapshot`で足から組み立てる。特別気配（`special_quote`）・値幅制限（`price_limit`）の足でのエントリー、貸株不可（`lendable=false`）銘柄のSHORTはライブと同様に再現から除外される（`ReasonSpecialQuote`/`ReasonPriceLimit`/`ReasonNotLendable`）
  - 残る差（実装済みの再現との差の一覧）: (1) Fast Screener・Jev Scoutは再実行せず、Jev Trader判断の有無で候補化を代用する。(2) 損益は価格リターン（%）の集計で、円建ての損益・数量は日次損失・エクスポージャの判定にのみ使う。(3) 指値の保留注文・部分約定は再現せず、成行のみ。(4) メタモデルの最低EV（Settings）・policy.*しきい値・Exit設定・リスク上限は履歴を持たないため、再現時点の値を全期間に使う。(5) モデルは保存済みの履歴だけを使い、再現中の学習はしない（モデルが無い期間はエントリー0件）。(6) `tdnet_score`はライブの現在のニュース状態ではなく、判断に記録された`news_context`から再構成する。(7) Kill Switch等の再現できない状態、FR-RISK-8の日次エントリー停止、手動再開（上記Risk Engineの項）。(8) 足は1分単位で、ライブのExit評価周期（保有ポジションの再評価サイクル）とは評価タイミングが一致しない場合がある。(9) 同時刻に複数銘柄の候補がある場合の判定順は設定した銘柄の並び順で、ライブのジョブ到着順とは一致しない
  - 窓をまたぐ判断: Walk Forwardの窓開始時点で既に記録済みの判断（前の窓・ウォームアップ区間で評価または失効した判断）は、次の窓で再利用しない（1判断→最大1エントリーを窓境界でも維持する）
  - 集計: Expectancy・平均利益・平均損失・Profit Factor・勝率・Max Drawdownはいずれも約定モデルのコスト（スリッページ・手数料）控除後の損益（`NetReturnPct`）で算出し、承認ゲート（FR-SELFIMPROVE-4）がコストを織り込む。コスト控除前の価格リターン合計は`GrossPnLPct`として別に出す。Max Drawdownの資産曲線は`ExitTimestamp`昇順で、同時刻に決済した取引は利益の大きい順に適用し（タイブレークは`EntryTimestamp`・銘柄・`InstrumentID`）、入力順に依存せず一意に決まる
  - データ読み込み: 再現は`market_snapshots`を`raw_data_json`抜きで読む（板全体は再現で参照しない）。Risk Engineの上限は銘柄をまたいで効くため、シャドーバックテストは全銘柄のRunConfigを一度に読み込み、ベースライン・提案後の2パスを1ポートフォリオとして再生する（1提案につきDB読み込みは1回。メモリには全銘柄分の足を保持する。Walk Forwardと同じ）
  - 副作用の無い評価: 再現は足ごとにPolicy Engineを評価するが永続化せず、運用ログ（`policy: trade signal decided`＝Signal count）も出さない
  - コストモデル（約定モデル）: エントリー・Exitの約定はPaper Tradingと同じ`fillmodel.Default`（FR-ENTRY-8）で価格付けし、バーの価格での全量約定にしない。呼値単位（買い切り上げ・売り切り下げ）・スプレッド（足の`bid`/`ask`、無ければ`spread_bps`の半分）・滑り（ザラ場2bps、寄り・引けの板寄せ5bps、不利な方向）・手数料（0bps。kabuステーションAPIを提供する証券会社の国内現物手数料が無料のため）を反映する。11:30〜12:30の昼休み・立会時間外の足は約定しない（その足でのエントリーは取引に計上せず判断は消費済み、Exit条件の評価は次の約定可能な足まで持ち越す）。寄り（9:00・12:30の足）と引け（15:25〜15:30の足）はスプレッドを跨がない板寄せ約定として別に扱う。Stop Loss/Take Profitのリターンは実際のエントリー約定価格を基準にする。Profit Factor・Expectancy・平均利益・平均損失はコスト控除前の価格リターン（足の価格間）、スリッページ込みPnLは約定価格間のリターン（スプレッド・滑り・呼値丸め・板寄せ込み、手数料なし）、手数料込みPnLは価格リターンから手数料のみを控除した値、Max Drawdownは約定価格間リターンから手数料も控除した累積リターンで算出する

  - **ラベル対再生の比較（オンデマンド計算）**: 同じ判断について、トリプルバリアのラベル上のnetリターン（`calibration_outcomes.net_return_bps`）と、その判断を実出口ルールで再生したnetリターンを並べ、差（再生−ラベル）の平均・標準偏差・パーセンタイルと、ラベルのTP/SL/タイムアウト到達数、再生の決済理由別件数、Paperの決済理由別件数（`positions.exit_reason`）を出す（`comparison`）。判断から約定足（FR-CAL-4の基準価格と同じ）までを`calibration_outcomes`・`market_snapshots`・`jev_decisions`から読み、足の価格で固定SL・固定TP・トレーリング・VWAP逆クロス・最大保有時間を同じ優先順で評価する。再生のコストはラベルと同じコスト（差が出口ルールだけになるように）、決済価格はトリガーした足の価格（ラベルはバリア水準）。Jev方向反転・continuation_probability低下（`response_json`内のみで列として読めない）・引け前強制決済は再生で評価できない（`not_evaluated_exits`に明示）。足が最大保有時間まで揃わない判断は`skipped_count`に数える。結果は保存せず、読み出しのたびに既存テーブルから計算する（新たな市場データの保存はしない）
  - **出口評価の共通化（issue #775との関係）**: 再生の出口判定は、Paper（`execution.Engine.EvaluateExit`）とバックテストの再生（FR-BT-4）が使う`internal/service/execution/exitcond.Evaluate`をそのまま呼ぶ（優先順位・トレーリングの基準・VWAP逆クロスを別実装にしない）。判定に使える入力が`market_snapshots`だけなので、Jev方向反転・continuation_probability低下・引け前強制決済は判断データ・Jevの再評価・当日の引け時刻を持たず再生できない（`not_evaluated_exits`で明示）。再生のコストはラベルと同じ（FR-COST-1の売買コスト設定を反映した方向別のラベルコスト）で、バックテスト本体（FR-BT-4、約定価格にスリッページ・手数料・貸株料を反映する）とは「約定価格ではなく足の価格にコストを引く」点が違う（ラベルと同じ定義で比べるため）
  - **OOS EVとPaper実績の並記**: 最新モデルの`oos_expected_value_bps`と、同じOOS期間（`oos_start`〜`oos_end`）に決済したPaperポジションの`realized_pnl`÷エントリー金額（手数料込み。bps）の平均を並べる（`oos_paper`）。決済済みポジションが無いときは平均を出さず「データ無し」と表示する。Paperの実績にはメタモデルによるゲートが掛かっていない期間の取引も含まれる点に注意（モデルの採用前後を分けた集計ではない）
- FR-CAL-5（勝ちの定義・判定水平線・実現PnL GT、issue #711）: 勝ちは「数分〜約15分のショートホールドで小さなエッジを積み上げる」ことと定義し、Outcome Labeling/Calibrationの判定水平線は`5 / 10 / 15`分（`calibration.DefaultHorizonsMinutes`・`scheduler.DefaultOutcomeLabelHorizonsMinutes`。トリプルバリア導入後（FR-CAL-4・issue #762）の実運用ではSettingsのtimeoutがその1水平線として積まれる）とする（旧`5/10/20`の20分は廃止。既存の20分`calibration_outcomes`行はそのまま残るが、新規には生成されない）。ground truthは2種を併用する: (1)価格パスGT（FR-CAL-4。`was_direction_correct`・`future_return`）、(2)**実現トレードPnL GT**。後者は、Jev Trader判断から生成された`trade_signals`→`paper_orders`（`positions.entry_order_id`）で建てられクローズ済み（`closed_at`と`realized_pnl`が非NULL）の`positions`を、その判断のconfidenceに結び付けたもので、`positions.realized_pnl`（円）は両約定の手数料控除後・約定モデル（FR-ENTRY-8）の呼値/スプレッド/滑りを織り込んだ値（追加の手数料・スリッページ仮定は置かない）、`return_pct`は`realized_pnl`÷エントリー想定元本（`entry_price × quantity`）×100。手動エントリー（シグナル紐付けなし）は含めない。`realized_pnl > 0`を「勝ち」とし（ちょうど0は勝ちでない）、confidence bucketごとに`trade_count`/`total_pnl`/`avg_pnl_pct`/`trade_win_rate`、全体で`trade_count`/`pnl_brier_score`/`pnl_log_loss`（confidenceを予測確率、勝敗を結果としたBrier Score/Log Loss）を`GET /api/v1/calibration`で返す
- FR-CAL-6（ホライズン別表示、issue #719）: Calibration集計（FR-CAL-2/3）は判定水平線（`5`/`10`/`15`分）ごとに切り替えて表示できる。`GET /api/v1/calibration?horizon=5|10|15|all`（既定`all`）が、ビン・方向別の表・Brier Score・Log Loss・ECEをそのホライズンの`calibration_outcomes`行だけで再計算する（`ListLabeledSamples*`が`horizon_minutes`で絞り、`LabeledSample`は`HorizonMinutes`を持つ）。`all`は現行水平線（`DefaultHorizonsMinutes`）に、トリプルバリアのラベル（`label_version=2`。horizonはSettingsのtimeoutで5/10/15以外もあり得る。FR-CAL-4・issue #762）を加えた合算で、#711以前の旧20分ラベルは既定の集計に含めない。Calibration画面は5/10/15/全体の切替ボタンを持ち、集計中のホライズンを常に表示する。実現トレードPnL（trades/JPY・PnL Brier/Log Loss）はホライズンに依存しない旨を画面に注記する。自己改善の日次分析（`DirectionMetricsSince`）も現行水平線のみを対象とする

Calibration集計（FR-CAL-2/3、`ListLabeledSamples*`・自己改善の日次分析）は`jev_decisions.question_version`で分離せず、全版の判断を混在して集計する。`question_version`は記録・表示（Decision history/Activity）用で、版を跨ぐ指標はプロンプト改訂直後に混在する点に注意

### 4.13 Jev RAG（経験ベース文脈拡張）

Jev Scout/Traderが「今の状態」だけでなく「過去の類似局面で何が起きたか」を踏まえて判断できるよう、過去データを検索し文脈として注入する。

- FR-RAG-1: `market_snapshots`（全スナップショット）および`jev_decisions`（判断が発生した局面。`calibration_outcomes`と紐付く）の各行に、標準化済み特徴量ベクトル（return_1m/5m/15m, price_vs_vwap_bps, volume_ratio_1m/5m, spread_bps, orderbook_imbalance, realized_vol_5m/15m, volatility_expansion_ratio, market_return_5m, sector_return_5m 等）を`market_snapshot_vectors`/`jev_decision_vectors`（sqlite-vec `vec0`仮想テーブル）に保存する
- FR-RAG-2: Jev Scout/Trader呼び出し直前に、現在の状態ベクトルに対しsqlite-vecで類似度上位k件（初期値k=5）を`jev_decisions`（`calibration_outcomes`紐付き済みのもの優先）および`market_snapshots`から検索する。紐付き済みの判断は、Scout判断（ラベル付与不能で全候補×毎サイクル索引される）が最近傍を占めていても候補から漏れないよう、紐付き済みのみを対象にした検索で先に最大k件取得する。問い合わせ対象の状態自身は類似事例に含めない（FR-RAG-4）
- FR-RAG-3: 検索結果（類似局面の方向・regime・実際のfuture_return・was_direction_correct等の要約）をJevへのプロンプトにfew-shot文脈として注入する。埋め込みはLLM API呼び出しを伴わない数値特徴量ベクトルのみを用い、追加のAPIコスト・レイテンシを発生させない
- FR-RAG-4: 蓄積データが不十分な期間（コールドスタート）はRAG文脈を空のまま呼び出す（Jevの通常判断のみで動作する）。サイクルごとに現在のスナップショット・Scout判断が検索前に索引済みのため、問い合わせ対象の銘柄・時刻（`Timestamp`）について、(a) 同一銘柄のScout/Trader判断のうち`Timestamp`が現在時刻以降のもの（Trader呼び出し直前に保存された同一状態のScout判断を含む）、(b) 補充枠の`market_snapshots`のうち同一銘柄で`Timestamp`が現在時刻−15分（特徴量ベクトルの最長ルックバック）より新しいもの（現在のスナップショット自身・直近の足）を検索結果から除外する。除外はKNN検索後にアプリ層で行う（k＋余裕分を取得して除外対象を落とし、除外対象でk件が埋まらない限り上位k件を返す。余裕分で足りなければ取得件数を広げて再検索する）。履歴全件を走査するサブクエリは使わない（issue #528）。他銘柄の同時刻スナップショット・判断は除外しない。除外の結果、類似事例が0件ならRAG文脈は空となる
- FR-RAG-5（将来拡張・未実装）: Symbol DetailのDecision historyに、参照した類似局面の件数を付加情報として表示する。任意要件でありUI必須要件ではない。現状は`jev_decisions`にも`GET /api/v1/symbols/{symbol}/decisions`の応答にも参照件数を保持・出力しておらず、`components/overview.md`にも対応する記述はない。実装する場合は、RAG Context Builderが検索した件数の保持先とAPI/UI表示を本書および`components/overview.md`に追記してから着手する

### 4.14 自己改善ループ（Luna / Sol / Opus 連携）

MVP必須要件ではないが、Phase 6（Continuous Loop）の一部として組み込む。「自己学習しながら継続的に改善する」ことを目的とし、高頻度の売買判断（Jev）とは分離した低頻度の振り返り・改善提案・検証・適用ループを構成する。Luna/Sol/Opusはいずれも実際の外部AI API呼び出しとして実装する（コード側のルールのみに依存しない、`architecture/overview.md` §8）。

| 役割 | 用途 | 呼び出し頻度 |
|------|------|------------|
| Luna（Sense） | ニュース分類・決算要約・bullish/bearish/neutral分類・イベント抽出 | リアルタイム補助（高頻度ループ内） |
| Jev（Decide） | 個別銘柄の売買方向・レジーム判断（RAG文脈込み） | 高頻度（§4.4, §4.5） |
| Sol（Think） | 負けトレード分析・相場環境変化分析・Jev誤判定クラスタ分析を行い、Policy Engineしきい値の改善提案（rationale付き）を生成する（既定はJev: 候補生成はコード、Jevが`choice`で選択。`integrations.md` §8） | 低頻度（日次、引け後） |
| Opus（Govern） | Solの改善提案をレビューし、直近の実績データでシャドーバックテスト検証した上で承認/却下する（既定はJevの`noul`採用確率。`integrations.md` §8） | Sol提案発生時のみ |
| Risk Engine（Control） | ポジションサイズ・損失上限等の最終拒否権。Sol/Opusからは変更不可 | 常時 |
| Execution（Act） | 発注・約定 | 常時 |

- FR-SELFIMPROVE-1: Sol は日次（引け後）に、直近の負けトレード・Calibration指標（Brier Score/ECE/confidence bucket別PnL）を分析し、`policy_proposals`に改善提案（`rationale_json`, `proposed_changes_json`）を記録する。直近20営業日のラベル付きCalibrationサンプル（LONG+SHORT合計）が30件未満の日は指標がノイズのためSolを呼ばず提案を作らない（AI障害ではないので`SkippedStages`ではなく情報ログに記録する）
  - 「引け後」は平日15:40 JST（大引け15:30の10分後）に固定する。cron式はホストのタイムゾーン（`time.Local`）ではなくJST固定ゾーンで解釈するため、ホストTZに依存しない（`internal/service/scheduler/selfimprove.go`）。祝日は考慮せず、祝日実行時は新規Calibrationデータなしで提案なしとなる
- FR-SELFIMPROVE-2: Solが変更を提案できる対象は`runtime_settings`の`policy.*`キー（Policy Engineのしきい値）に限定する。`risk.*`キー（Risk Engineのリミット値）および Jev の`prompt_version`/質問セット自体は自己改善ループの対象外とし、人手のみが変更できる（`docs/overview.md`「含まないもの」の「AI（Jev/Sol/Opus）による Risk Engine のリミット値そのものの変更」を継続遵守）
- FR-SELFIMPROVE-3: 1提案あたりの変更幅は confidence系しきい値で±0.05、entry_quality等の段階型しきい値で1段階までを上限とする
- FR-SELFIMPROVE-4: Opusは提案を受け取ると、直近の`trade_signals`/`jev_decisions`/`calibration_outcomes`（直近30営業日相当（FR-SELFIMPROVE-1のCalibration指標は従来どおり直近20営業日）。営業日は東証の取引日＝`marketcalendar.TSE.IsTradingDay`（土日・祝日・振替休日・国民の休日・12/31〜1/3の年末年始休場を除く）で数える）に対し提案後しきい値を適用した場合のExpectancy・Max Drawdownをシャドーバックテスト（バックテストエンジン§4.11を再利用。ライブと同じ判断フロー（その時点で有効だったメタモデルのtake/skip・Risk Engine・FR-EXIT-1の全Exit条件・固定コストモデル）を再生した比較値で、残る差はFR-BT-4に一覧する）で算出し、既存policy_versionに対しExpectancyが悪化せずMax Drawdownの悪化が許容範囲内（相対10%以内）の場合のみ承認する。エントリー可否はメタモデルの判定（FR-POLICY-6）でライブと同じく`min_probability`を使わないため、`min_probability`だけを変える提案は再現上の取引が変わらず（Expectancy・Max Drawdownは同一）、承認ゲートはその変更の効果を測れない。ベースライン・提案後のどちらかのシャドーバックテスト取引件数が**100件未満**、または対象期間が**30営業日未満**（`assist.MinBacktestTrades`=100・`assist.MinBacktestDays`=30。issue #780の決定・2026-10-19）の場合は比較に証拠がない（取引0件なら双方Expectancy 0/Max Drawdown 0で「悪化なし」に見えてしまう）ため、Opus APIを呼ばず`insufficient_samples`理由で却下する。この件数・日数は**足切りであり、安全の証明ではない**（超えても偶然の結果は残り得る）。数字は仮定つきで、リターンの保証ではない。対象期間より前に有効なメタモデルが無い場合も取引0件となりこの却下になる（FR-BT-4）
- FR-SELFIMPROVE-5: 承認された提案は新しい`policy_version`（`sol-<提案id>`）として`runtime_settings`に自動適用し、`policy_proposals.status`を`applied`に更新する。却下時は`rejected`として理由を記録する。適用に失敗して`approved`のまま取り残された提案は、次回の日次バッチ冒頭で適用を再実行して`applied`へ収束させる（Slack通知の失敗は適用結果に影響させず、ログ記録のみのbest-effort）。適用中の`policy_version`はライブシグナルの`trade_signals.policy_version`に`policy-v1+sol-12`の形で記録される（FR-POLICY-5）
- FR-SELFIMPROVE-6: 適用後5営業日（東証の取引日、FR-SELFIMPROVE-4と同じ数え方）相当のExpectancy（窓内にクローズ済みのポジションの`realized_pnl`平均）が適用前の同じ長さの窓より相対20%以上悪化した場合、自動的に直前の`policy_version`へロールバックし、Slack通知する（通知失敗はロールバック結果に影響させずログ記録のみ）。ロールバックは、その提案が書いた各キーが`runtime_settings`上で今もその提案の適用値のままの場合に限りOldValueへ戻す（後続提案・手動変更が既に値を変えたキーは上書きせず、`rolled_back_reason`に未変更のキー名を残す）。戻す先が既にロールバック済みの提案の適用値であればその提案の適用前の値まで遡り、ロールバック済み提案の値を復活させない。「相対20%以上悪化」は`post < pre`かつ`pre - post >= |pre| × 0.20`（適用前が負でも`|pre|`を基準にし、`pre == 0`では`post < 0`のみ）で判定し、`post >= pre`（改善・同値）では決してロールバックしない。適用前または適用後のどちらかの窓にクローズ済みポジションが0件のときは「判定不能」としてロールバックしない（しきい値の厳格化で約定が0件になっても誤ロールバックしない）。判定不能の提案は`status=applied`のまま残り、追跡窓が閉じた後も打ち切らず、以降の日次実行のたびに再評価する（窓は適用時刻を基準に固定のため、窓内のデータが揃うまで判定されない）
- FR-SELFIMPROVE-7: Sol/Opusの提案・レビュー・適用・ロールバックはすべて`policy_proposals`と`runtime_settings`の変更履歴として監査可能な形で保存する
- FR-SELFIMPROVE-8: Solが生成した`proposed_changes_json`は、`selfimprove`サービスがFR-SELFIMPROVE-2（対象キーは`policy.*`のみ）・FR-SELFIMPROVE-3（変更幅上限）を機械的に検証する。逸脱する提案は`policy_proposals.status=rejected`（`review_json.reason=llm_output_out_of_bounds`）として却下し、LLM出力の内容を無条件に信用しない
- FR-SELFIMPROVE-9: Opusの承認判定は、既存の決定的シャドーバックテストしきい値（FR-SELFIMPROVE-4）とOpus APIによる定性レビューの両方を満たした場合にのみ`approved`とする。Opus APIは決定的しきい値を満たす提案を追加で却下できる（安全側の拒否権）が、決定的しきい値を満たさない提案を承認へ覆すことはできない
- FR-SELFIMPROVE-10（変更頻度の制限と凍結、issue #780・親 #752）: `policy.*`しきい値の変更は、(a) 前回の変更（提案の適用または自動ロールバック。`policy_proposals.applied_at`・`rolled_back_at`の最新）から**5営業日**（東証の取引日、FR-SELFIMPROVE-4と同じ数え方）空け、(b) メタラベリングの有効モデルを採用してから**3営業日**は行わない（`internal/service/changeguard`、`selfimprove.WithChangeGuard`）。メタモデルの再学習による入れ替えと自己改善の変更が同じ窓に重ならないようにし、成績の変化をどちらの変更によるか切り分ける（メタモデル側の制限はFR-META-7）。判定はOpusのレビュー（シャドーバックテスト）の前に行い、制限内の提案は適用せず`status=rejected`・`reviewed_by=governor`・`review_json.reason`（`policy_change_rate_limited`＝前回の変更から5営業日未満、`model_adoption_freeze`＝モデル採用から3営業日未満）・`review_json.detail`（経過日数と解除日）を記録してWARNログに出す（`policy_proposals`から後で監査できる）。承認済みで適用に失敗した提案の再適用（FR-SELFIMPROVE-5）と、FR-SELFIMPROVE-6の自動ロールバックは安全側の操作として制限しない（ロールバックは「変更」として次の制限の起点になる）。変更幅の上限（FR-SELFIMPROVE-3）・承認ゲート（FR-SELFIMPROVE-4）・日次ガードの既定値は変えない。

### 4.15 System Activity Feed

Scheduler/Jev/Risk Engineが「現在何を実行しているか」をUIから確認できるよう、既存テーブル（`jobs`, `jev_decisions`, `kill_switch_events`）を集約したリアルタイムフィードを提供する。Calibration/監査で使う既存データの保持方針（`non-functional.md` §5.1のログローテーション、各テーブル自体の保持期間）は変更しない。新規の永続テーブルは追加しない。

- FR-ACT-1: `jobs`テーブルをキュー別（`market-data`/`feature-calc`/`jev-scout`/`jev-trader`/`outcome-labeling`/`analytics`の6キュー。`feature-calc`はフルスキャンがenqueueしないため通常0件）に集計し、`pending`/`running`/直近`failed`件数を提供する。`outcome-labeling`の「まだラベル付けできない」（pending再試行）と「恒久的にラベル不能」（skip、`succeeded`で終了）は`failed`に数えない（FR-CAL-4、issue #710）。直近`failed`件数は`finished_at`が集計時刻（`as_of`）から過去1時間（固定。設定では変更できない。`activityfeed.FailedWindow`）以内の`failed`ジョブの件数で、1時間より前に失敗したジョブは数えない。`GET /api/v1/activity`の`failed_recent`と`/ws/activity`の`job_update.failed_recent`で同じ窓を使う
- FR-ACT-2: `jobs`の状態遷移、`jev_decisions`の新規登録（Scout/Trader呼び出し）、`kill_switch_events`の発生を時刻順にマージした単一のアクティビティフィードを提供する

### 4.16 Luna ニュース分類・News Ingest

News Ingest（`internal/service/newsfeed`）が対象銘柄に関連するニュース見出し・本文をニュースフィード（既定: やのしんTDnet WebAPI、キー不要）から取得し、Luna（既定: Jev。`LUNA_*`で別の外部AIへ差し替え可）へ送信して市場コンテキストを補強する。Luna・Sol・Opusは既定でJev（`JEV_API_KEY`のみ）で動き、`LUNA_*`/`SOL_*`/`OPUS_*`は役ごとの任意の差し替えである（未入力の役はJevにフォールバック。`architecture/overview/integrations.md` §8・§13）。永続化は既存カラムの範囲内で行い、新規テーブルは追加しない。

- FR-LUNA-1: News Ingestは、ニュースが実際に参照される銘柄（直近のFast Screener候補と保有中ポジションの銘柄）のみを対象に、東証立会時間中だけ、少数（既定4）の並列で、ニュースフィードから見出し・本文を定期取得する。既定はやのしんTDnet WebAPI（`https://webapi.yanoshin.jp/webapi/tdnet/list/{銘柄コード}.json`、API キー不要、銘柄単位、1分周期、記事ID（無ければ見出し）で重複排除）で、`NEWS_FEED_URL`/`NEWS_FEED_API_KEY`でユーザー指定の汎用フィード（`{"items":[{id,headline,body,published_at}]}`）へ差し替え、`NEWS_FEED_ENABLED=off`で停止（News Ingestを起動しない）できる。やのしんの応答（`items[].Tdnet`/`TDnet`/フラット）は`newsfeed`のアダプタで同契約へ正規化する（PDF取得・`release.tdnet.info`のスクレイピングはしない）
- FR-LUNA-2: 取得したニュース1件ごとにLuna（既定Jevの`choice`質問。`LUNA_BASE_URL`設定時はそのLuna API）へ送信し、`sentiment`（bullish/bearish/neutral）・`event_type`（決算/業績修正/M&A/規制/その他）・`summary`を受け取る
- FR-LUNA-3: Luna応答は当該銘柄の直近ニュース文脈としてインメモリキャッシュ（直近N件、TTL付き、DB非永続）に保持し、Jev Scout/Trader呼び出し時に`jev_decisions.state_json`（既存カラム）内の`news_context`フィールドとして注入する。これによりFR-SCAN-1の「ニュースフラグ発生」トリガーを実装する
- FR-LUNA-4: Luna失敗時、およびニュースフィード（やのしん等）の停止・遅延・タイムアウト時は、ニュースフラグを立てずその銘柄をスキップし、通常のFast Screener/Jev/発注フロー・起動に影響を与えない（Jev同様、失敗時は機能低下のみでシステム全体を止めないフェイルセーフ）。フィード取得は短いタイムアウトとし、連続失敗時はバックオフして問い合わせ頻度を落とす。エラーはログとSystem Activity Feed（`news_feed`）に出す。Jev・フィードが使えなくても起動は失敗しない（issue #273）
- FR-LUNA-5: Lunaの分類結果はJevの判断そのものを上書きしない。あくまでJev Scout/Traderへの補助的な文脈情報としてのみ用いる（`architecture/overview.md` §8「Lunaは高頻度側の補助コンポーネント」の方針を継続）
- FR-LUNA-6（TDnet開示スコア、issue #763・親 #752）: `newsfeed.Service.TDnetScore(symbol, at)`（純関数`newsfeed.ScoreNewsContext(items, at, ttl)`への委譲。学習側は`jev_decisions.state_json`の`news_context`から判断時点のスコアを同じ規則で再計算する）は、FR-LUNA-3のキャッシュにある当該銘柄の開示のうち`(at-TTL, at]`に公開されたものについて、Lunaの`sentiment`（bullish=+1 / bearish=-1 / neutral・不明=0）に鮮度の線形重み（公開直後1、TTL経過で0）を掛けた和を`[-1, 1]`にクランプした値を返し、メタモデルの特徴量`tdnet_score`（FR-META-1）として使う。`at`より後に公開された開示は無視する（先読みしない）。有効な開示が無い銘柄（キャッシュなし・TTL切れ・未来のみ）は中立の`0`を返す（「算出不能」ではない）。スコアはFR-LUNA-5のとおりJevの判断を上書きせず、二次モデルの入力としてのみ用いる。

### 4.21 取引ログ・判断ログのエクスポート（issue #768。実装は#770〜#773）

- FR-MCP-8: 受け入れ条件は API 仕様 §5。テスト用 DB で集計値が手計算と一致し、認証失敗が SQL 0 件であり、戻り値とログに生データと秘密が含まれないことを自動テストで確認する。選んだ経路（Tailscale または Cloudflare Tunnel）経由の実機確認は自動テストの外とし、キーを伏せた記録を残す。Tailscale のときは tailnet の外から届かないことも記録する
- FR-MCP-9: Settings 画面（`GET /settings`）の「外部連携」節に、カード「MCP（Paper 実績・Jev 判断の読み取り専用エンドポイント）」（`settings-card-mcp`、モーダル `modal-mcp`、`/settings#modal-mcp`）を置く。中身は `GET /settings/mcp-panel` を `load` で取得するフラグメントで、`/settings` 本体は TCP 接続しない。カードは MCP 設定サービスが配線されたときだけ表示する。パネルは、状態（待受中／起動中／停止中／エラー／キー未設定）、「次回起動時も自動で起動する」表記、起動・停止・再起動のボタン（FR-MCP-13）、有効化のチェック、待受アドレス、API キーの生成・再生成、Grok Bot に登録する値（URL と、伏せ字の `Authorization: Bearer ●●●●●●●●`）、`paper-results-mcp` の配置先（アプリ本体と同じフォルダ。見つかる／見つからない）、設定ファイルの場所を示し、MCP は本体の子プロセスとして「起動」で起動し、設定変更の反映には「再起動」が要ることを書く（FR-MCP-13〜16）。受け入れ条件: 設定ファイルが無ければ「停止中（無効）」で TCP 接続しない／有効でキーが空なら「キー未設定」で接続しない／有効でキーがあり接続できれば「待受中」、できなければ「停止中」（アプリが起動してから 10 秒以内は「起動中」、起動失敗・異常終了は「エラー」）。設定ファイルが読めない・権限が緩いときは「停止中」と警告を示し、キーの内容は出さない
- FR-MCP-10: 有効/無効と待受アドレスの保存（`POST /settings/mcp`）は、サーバー側で FR-MCP-1 と同じ規則を検証する。許すのは `127.0.0.1`・`::1` と、この PC のインターフェースにある tailnet アドレス（IP リテラルの `host:port`）だけ。`0.0.0.0`・`::`・ホスト部が空・LAN・ホスト名・ポート 0・この PC に無い tailnet アドレスは 422 で拒否し、設定ファイルは変えない。空欄は `127.0.0.1:48110`。保存は API キーと Cloudflare Access の項目を保つ。ファイルは一時ファイルに書いて fsync し rename で置き換える（`0600`）
- FR-MCP-11: API キーの生成・再生成（`POST /settings/mcp/key`）は、`pitha-mcp-` ＋ 32 バイトの乱数のキーを設定ファイルにだけ保存し、その応答に一度だけ表示する（読み取り専用の欄、`Authorization: Bearer <キー>` の全文、コピーボタン、再表示しない旨）。応答は `Cache-Control: no-store`、表示部は `hx-history="false"` と `autocomplete="off"`。以後のパネル・`/settings`・ログには、キーの文字を一切出さず伏せ字だけを出す。再生成の確認では、古いキーが（MCP の再起動後に）使えなくなると伝える
- FR-MCP-12: API キーは DB（`secrets` を含む）に保存せず、ログ・データエクスポート（FR-EXPORT）・DB バックアップ・`View` の文字列化に入れない。保存・再生成のログに出すのは `enabled` / `listen` / `key_configured` だけである。受け入れ条件: 生成後の `GET /settings`・`GET /settings/mcp-panel`・保存応答、取得したログ、エクスポート ZIP、バックアップ（日次・週次）、DB ファイルにキーのバイト列が含まれないことを自動テストで確認する
- FR-MCP-13: MCP の起動・停止・再起動を Settings 画面の MCP パネルから行える（`POST /settings/mcp/start`・`stop`・`restart`、issue #795）。MCP は別プロセスのまま、アプリは `paper-results-mcp` を子プロセスとして起動するだけで、アプリの DB 接続・書き込み権限・開いているファイル・アプリの環境変数（許可リスト以外）は渡さない。API キーは起動引数・環境変数・ログ・画面・プロセス一覧に出さず、`0600` の設定ファイルから子が読む。起動は、保存された設定が有効・API キーあり・待受アドレスが許可範囲のときだけで、満たさないときはプロセスを作らない。待受アドレスがすでに応答している・アプリが起動した子がいるときは二重に起動しない。3 つの操作はセッション Cookie と CSRF トークンが必須で、Setup 完了前は閉じる。GET では何も起動しない
- FR-MCP-14: 状態表示は 停止中／起動中／待受中／エラー（＋キー未設定）。起動失敗（実行ファイルなし・OS が起動できない）、異常終了（操作者の停止でない終了）、起動から 10 秒たっても待受しない場合は「エラー」とし、理由は固定文（ポート使用中・待受拒否・設定ファイル不可・終了コードなど）で出す。プロセスの出力そのものは出さない。画面に「再起動」ボタンを置く。自動で再起動し直すループは作らない。アプリの外で起動された MCP は「待受中」と併記し、画面からは停止しない
- FR-MCP-15: アプリ起動時、保存された設定が有効・API キーあり・待受アドレスが許可範囲なら、MCP も同時に起動する。無効（既定）・キー空・不正アドレス・設定ファイルが使えないときは起動しない。画面の状態表示に「次回起動時も自動で起動します」（起動しないときはその理由）を出す。アプリ終了時は MCP も止める。Windows ログオン時のアプリ自動起動（スタートアップショートカットの `--supervise`、`non-functional.md` §3）はすでにあり、新しい自動起動は作らない。PC 再起動後はその経路でアプリと MCP が復帰する（ホスト再起動後の無人復帰は Windows の自動ログオンが前提）。待受アドレスが tailnet アドレスでまだ PC に割り当てられていない（ログオン直後で Tailscale が上がっていない）ときだけ、最大 90 秒待ってから判定し直す
- FR-MCP-16: アプリが異常終了・kill されても MCP が孤児で残らない（Windows は子を一時停止で作り、Job Object の kill-on-close に入れてから動かす。Linux は `Pdeathsig`）。`--supervise` によるアプリの再起動後に MCP も復帰し、前の MCP のポートが閉じるまで待ってから起動し、二重に起動しない。受け入れ条件: 自動起動する／しない条件、二重起動しない、キー平文が出ない（引数・環境・ログ・画面・子の出力）、アプリ終了時に止まる、アプリを kill しても孤児が残らない、起動失敗・異常終了が状態に出る、3 つの API が CSRF 対策済み・認証必須であることを自動テストで確認する（設計は `architecture/paper-results-mcp-lifecycle.md`）

### 4.23 Settings の構成（issue #793・#805）

管理系の画面・機能（Settings の各ダイアログを含む）は、メインナビの「Settings」1つから辿れる。「Settings」（`GET /settings`）はページの一覧で、各ページ（`GET /settings/<page id>`）が詳細設定と関連画面へのリンクを持つ。旧「管理ハブ」（`GET /admin`、issue #793）は #805 で Settings に統合した。一覧は画面名・URL・できること・ページの表（`docs/components/screens.md`）と同じ内容を持つ。

- FR-ADMIN-1: `GET /settings` は、運用／成績・検証／リスク・資金／ブローカー・データ／外部連携／ログ・エクスポートの6ページ（`/settings/operations`・`results`・`risk`・`broker`・`integrations`・`maintenance`）への名前・要約・リンクを載せる。各ページは、そのページに属する接続先・設定項目・システムのカード（`/settings/<page id>#<ダイアログ id>` でダイアログを開く）と、Settings の外の関連画面（Scanner・Performance など）へのリンクを載せる。専用 URL を持たない Kill Switch は、ヘッダーのパネルがあるページ（`/scanner#kill-switch`）へ誘導し、その旨を説明に書く。`/swagger` は `SWAGGER_ENABLED=true` のときだけ載せる。
- FR-ADMIN-2: Settings 画面の全カード（接続先・設定項目・システム）は、ちょうど1つのページに置かれ、そのページから開ける。全運用設定キー（`opsettings.Keys()`）は、いずれか1ページで編集できる。カードを足すときは同時にそのページを決める（`internal/web/settingspages` の登録簿。完全性は router 層・handler 層のテストで検査する）。今後の設定グループ・ページの追加も登録簿への追記で足りる。メインナビの各項目（Settings 自身を除く）は、いずれかのページのリンクに載る。
- FR-ADMIN-3: 既存の画面の URL・API・ルートは変えない。`/` は `/scanner` へ、`/setup` は Setup Guard の既存挙動のまま。旧 `/admin` は `/settings` へ 301 でリダイレクトする。旧 `/settings#modal-<id>`（ハッシュ付きの直リンク。ヘッダーのバージョン表示の旧リンク先 `#update-panel` を含む）は、一覧ページの対応表を元にクライアント側で `/settings/<page id>#<id>` へ転送する。`/settings` と各ページは他のページと同じく Setup Guard の対象で、必須の接続が未設定の間は `/setup` へ送る。
- FR-ADMIN-4: `layout.Shell` を使う全ページのメインナビは「Settings」1項目で、単独の「管理」は置かない。「Settings」は `/settings` とその下のすべてのページで `aria-current="page"` を付け、各ページはパンくずからも一覧へ戻れる。例外は `/setup`（ヘッダーを持たない初回専用画面）と `/swagger`（静的なドキュメント画面）。
- FR-ADMIN-5: Symbol Detail（`/symbols/:symbol`）はパラメータ付きで Scanner の候補から開く画面のため、Settings のページにはリンクを置かず、画面一覧の表にだけ載せる。
