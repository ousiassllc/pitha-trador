### 4.1 Feature Engine

市場データから以下の特徴量を算出する。

| カテゴリ | 特徴量 |
|---------|--------|
| 価格 | return_1m/3m/5m/15m/30m, high_distance_5m, low_distance_5m, session_high_distance, session_low_distance |
| VWAP | vwap, price_vs_vwap_bps, vwap_slope, vwap_cross_direction |
| 出来高 | volume_1m/5m, volume_ratio_1m/5m, turnover_1m/5m |
| ボラティリティ | atr_1m/5m, realized_vol_5m/15m, volatility_expansion_ratio |
| 板・約定（取得可能な場合） | best_bid, best_ask, spread_bps, bid_depth, ask_depth, orderbook_imbalance, buy_trade_ratio, sell_trade_ratio, trade_flow_imbalance, microprice, microprice_dev_bps |
| 板の需給（OFI、issue #750） | ofi_short, ofi_mid, ofi_long（既定10秒/30秒/60秒の窓）と、その窓幅`ofi_window_short_seconds`/`ofi_window_mid_seconds`/`ofi_window_long_seconds` |
| 市場コンテキスト | TOPIX/Nikkei225 return_1m/5m, sector_return_5m, stock_vs_sector_relative_strength, market_breadth |

- FR-FE-1: すべての特徴量は判定時点までのデータのみで算出する（look-ahead防止、§4.11 バックテスト（FR-BT-3）参照）
- FR-FE-2: 板・約定特徴量はkabuステーションAPIから取得できない銘柄・時間帯では欠損値として扱い、依存するJev入力/スコアから除外する。bid/askが逆転した板（bid > ask）も無効として`spread_bps`/`microprice`を欠損とし、スプレッド上限ガードが負値を素通りしないようにする
- FR-FE-3: `volume`/`turnover`はkabuステーションAPIの当日累積値である。`volume_1m/5m`・`turnover_1m/5m`は「現在の累積値 − 窓の開始時点の累積値」で算出し、足の合算はしない。Fast Screenerの`min_turnover_5m_jpy`とPolicy Engineの「板が薄い」判定は同じ`turnover_5m`（`featureengine.TurnoverOverWindow`）を用いる
- FR-FE-4: 市場コンテキストは`instruments.kind`で区別した追跡銘柄から算出する。`market_index`（TOPIX/Nikkei225等）のreturn平均を`market_return_1m/5m`、銘柄の`sector`と一致する`sector_index`のreturnを`sector_return_5m`とし、`stock_vs_sector_relative_strength = return_5m − sector_return_5m`、`market_breadth`は「許容年齢」以内の全アクティブ株式の最新return_5mの（上昇数−下落数）/銘柄数とする。追跡銘柄が未登録・最新の足が許容年齢を超えて停止・履歴不足の場合は欠損値とする（FR-FE-2と同じ扱い）。許容年齢は、ランキング監視では`domain.MarketContextMaxAge`（3分。指数バーは60秒周期で更新されるため3周期分。`stale_snapshot`の許容とは別。FR-FE-7）、`scan.full_scan_enabled: true`は全件REST1周に合わせた`scan.full_scan_max_snapshot_age_seconds`（同梱620秒）とする（`marketdatajob.Handler.MarketContextMaxAge`＝`ScanConfig.SnapshotMaxAge(domain.MarketContextMaxAge)`を`marketcontext.NewLoader`へ注入。issue #692）。**ただしこの許容年齢が緩めるのは「最新の足の鮮度判定」だけ**で、`market_return_1m/5m`・`sector_return_5m`の窓の基準バーの許容（FR-FE-5。1分窓は90秒、5分窓は150秒）は変わらない。`scan.full_scan_enabled: true`では指数行の足も全件RESTの1周（約8分）に1回しか書かれず基準バーが許容外になるため、620秒を設定しても`market_return_1m/5m`・`sector_return_5m`は常に欠損になり、`market_breadth`も標本となる株式の`return_5m`が欠損のため算出されず、FR-RISK-1の`market_adverse_to_direction`ゲートは`market_return_5m`欠損の素通りとなって機能しない。これは仕様上の制約で、基準バーの許容は「N分モメンタム」の誤認を避けるために全件スキャンでも広げない（issue #693/#694/#696）。サポートする運用は既定のランキング監視（FR-SCHED-9。足が毎分更新される）で、全件スキャンの履歴ベース特徴量の欠損はFR-FE-5・FR-SCHED-7を参照する。算出値のキャッシュ（30秒）は許容年齢より十分短い。既定のランキング監視（FR-SCHED-9）では指数行（`market_index`と監視銘柄の`sector`の`sector_index`）も毎サイクル取り込まれるため`market_return_*`・`sector_return_5m`は算出されるが、`market_breadth`の「全アクティブ株式」のうち許容年齢（3分）以内に更新されるのは監視銘柄（最大45）だけなので、監視銘柄の上昇・下落比になる
- FR-FE-5: 窓（`return_*`・`vwap_slope`・`volume_*`・`turnover_*`・`vwap_cross_direction`等）の基準バーは、窓開始時刻（判定時刻−窓幅）から「窓幅の50%（最小90秒）」以内に存在しなければならない。それより古い基準バー（前営業日の引け・昼休み前の前場最終バー・再起動/欠測をまたぐバー）しか無い場合は履歴不足として欠損値（nil）とし、ギャップを「N分リターン」として扱わない（`featureengine.windowRef`）。**`realized_vol_*`はこの列挙の対象外**で、窓開始の基準バーを要求せず、窓内の1分刻みの各マークごとに直近バーを90秒（`minRefTolerance`）以内の許容で探して1分リターンを作り（それより古いバーしか無いマークのリターンは除く）、2本以上のリターンが得られれば算出する（得られなければnil。`featureengine.realizedVol`）。このため`realized_vol_15m`は履歴が3分程度でも非nilになりうる（部分窓の値）。この値は`volatility_expansion_ratio`・Fast Screenerの`min_realized_volatility`にそのまま流れる
  - 全件スキャン（`scan.full_scan_enabled: true`。FR-SCHED-7）では各銘柄の足が全件RESTの1周（約8分）に1回しか書かれないため、1分・3分・5分窓（許容90秒〜150秒）の基準バーが存在せず、`return_1m/3m/5m`・`volume_*`・`volume_ratio_*`・`turnover_1m/5m`・`vwap_slope`・`realized_vol_*`（1分刻みのマークごとに90秒以内の足が必要）などの短窓の履歴ベース特徴量は全銘柄で常に欠損になる（15分・30分窓の`return_15m/30m`は許容が7.5分・15分のため算出されうる）。Fast Screenerは全銘柄を`missing_return_5m`等の欠損として除外し候補は空のままになる。上記の許容は全件スキャンでも広げない（8分間の変化を「5分リターン」として扱う誤認を避けるため）。全件スキャンは履歴ベース特徴量が算出できない運用で、サポートする運用は既定のランキング監視（FR-SCHED-9）。起動時に警告ログを1回出す（FR-SCHED-7。issue #693）
- FR-FE-6（板の需給偏り・マイクロプライス、issue #750）: kabu PUSHの最良気配（Bid/Ask価格・数量）の更新ごとに、Cont–Kukanov–Stoikov（arXiv:1011.6402）のOrder Flow Imbalanceのイベント値`e = 1{Pb>=Pb'}·qb − 1{Pb<=Pb'}·qb' − 1{Pa<=Pa'}·qa + 1{Pa>=Pa'}·qa'`（買い圧力が正、株数、プライムは直前の気配）を銘柄ごとに累積し（`internal/service/orderflow`）、ローリング窓（既定10秒/30秒/60秒）の合計を`ofi_short`/`ofi_mid`/`ofi_long`としてバーごとに`market_snapshots`へ保存する。窓幅は`runtime_settings`の`orderflow.ofi_window_{short,mid,long}_seconds`（整数秒、`1 <= short < mid < long <= 600`）で、Settings画面の「板の需給（OFI）」から再起動なしで変更でき（envにはしない）、バーに使った窓幅もバーごとに保存する（後から窓幅を変えても保存値を解釈できる）。`microprice_dev_bps`は`(microprice − mid)/mid × 10000`（bps）。欠損・異常時の扱い: 気配または数量が欠けた板、数量が0以下の板（片側が空）、価格が0以下・非有限の板、bid > askの逆転板、特別気配（`BidSign`/`AskSign`が特別気配・板寄せ等）はOFIのイベントを作らず、直前の板との連鎖も切る（次の有効な板が新しい起点になり、板寄せ前後をまたいだイベントは作らない）。窓内にイベントが1件も無いときは0ではなくNULL。`microprice_dev_bps`はmicropriceがNULLまたはmidが0以下のときNULL。いずれの場合もNaN・Infを生成せず0除算しない。OFIはPUSHの最良気配のみから計算し（RESTポーリングは更新が疎なため対象外）、kabu以外（立花）のブローカーではNULL。**OFI・マイクロプライスは特徴量・フィルタ（メタラベリングの入力）であり、単独の売買シグナルにはしない**（これらだけで発注する経路は作らない）。Jevへの入力（`state_json`・`state_hash`）には含めない（OFIの揺らぎがFR-SCAN-2の再評価抑制を壊すため）。代わりに判断（`jev_decisions`）ごとに、判断時点のスナップショットのOFI・窓幅・マイクロプライス乖離を同じカラム名で保存する（学習・分析用）。検証はpaperのみで、live（#55）は対象外
- FR-FE-7（足の鮮度上限・PUSH優先・判断時点のデータの古さ、issue #754）: ランキング監視（`scan.full_scan_enabled: false`）で、Jev Scout/Trader・Paper Entry・Scannerの`stale_snapshot`が最新の足を古いとみなす上限は、`runtime_settings`の`scan.snapshot_max_age_seconds`（整数秒、`1〜600`、既定`domain.DefaultMaxSnapshotAge`＝20秒。Settings画面の「データの鮮度（ランキング監視）」。環境変数・yamlでは設定しない）で、起動時に読み込む（変更の反映には再起動が必要）。5〜15分先を狙う判断を1分前の足で行わないための引き締めで、足は約60秒周期で書かれるため、20秒以内の足で判断できるのは足の更新直後（イベント起点の再評価を含む）に限られる。`scan.full_scan_enabled: true`では従来どおり`scan.full_scan_max_snapshot_age_seconds`（同梱620秒。FR-SCHED-7）を使い、この設定は無視される。価格はkabuのPUSHを優先する: `pushfeed.Feed.Latest`は鮮度上限（`Feed.BoardMaxAge`＝この設定値。未設定は`pushfeed.DefaultBoardMaxAge`＝20秒）以内に受信したPUSH板があればそれを使い、古い・未着のときだけREST（`GET /board`）へ戻す。Jevへ渡すstate（`ScoutState`）は判断時点での足の古さ`data_age_ms`（判断時刻−足の時刻、ミリ秒、0以上の整数）を含み、同じ値を`jev_decisions.data_age_ms`に保存する（Scout・Trader共通。`state_hash`は`data_age_ms`を含むためjitterする）。検証はpaperのみ（liveは#55のblockedのまま）

### 4.2 Fast Screener

- FR-FS-1: Jev API呼び出し前に、`config/strategy.yaml`/DB設定値（`min_price`, `max_price`, `min_turnover_5m_jpy`, `max_spread_bps`, `min_volume_ratio`, `min_abs_return_5m_pct`, `min_realized_volatility`）で明らかに対象外の銘柄を除外する（全フィルターを評価して除外理由を保持し、Scanner Dashboardのスキャン状況パネル（FR-SCAN-3〜6、除外・欠損理由の表示は FR-SCAN-4/5）で銘柄別に参照できる。値が欠損の銘柄は閾値未達ではなく欠損理由として区別する。約定不能な足も同じくJev呼び出し前に除外する（issue #511）: **特別気配**（板の`BidSign`/`AskSign`が`0102`特別気配・`0108`停止前特別気配。理由`special_quote`）と**ストップ高/ストップ安**（現値が銘柄情報`UpperLimit`/`LowerLimit`に到達。理由`limit_up`/`limit_down`）は、スナップショットの`special_quote`/`price_limit`から判定され、除外理由としてScanner Dashboardに表示される（欠損ではなく`excluded`）。ショート方向が確定するのはJev Trader後のためFast Screenerでは貸借を見ず、貸借なしのショートはFR-POLICY-3で外す。`min_abs_return_5m_pct`の単位は**パーセント**（0.3 = 0.3%）で、Feature Engineの`return_5m`（小数比、0.003 = 0.3%）を×100して比較する）
- FR-FS-2: 通過銘柄に対し以下のスコアを算出し、上位N銘柄のみJev Scoutへ送る。Nは`fast_screener.top_n`で、同梱既定は20（`config/strategy.yaml`。Jev APIコストを抑える側の値）。50〜200へ引き上げる場合は`non-functional.md` §2.1のAPI呼び出し上限（Nに比例）を確認する

```text
screen_score =
  w1 * normalized_volume_ratio   # = volume_ratio_5m（下記）
+ w2 * abs(return_5m)   # return_5mは小数比（%換算しない）
+ w3 * breakout_strength
+ w4 * orderbook_imbalance
+ w5 * volatility_expansion
```

  - `normalized_volume_ratio`: Feature Engineが算出する`volume_ratio_5m`（5分出来高の現在値/平均の比率。通常1.0前後）をそのまま用いる。追加の正規化・キャップ・スケーリングは行わない（実装は`screener.ScreenScore`が`weights.volume_ratio * volume_ratio_5m`を加算する）。「正規化済みの比率」という意味でのみ`normalized`と呼ぶ。履歴不足で算出できない場合は下記のとおり項ごと欠損として除外する
  - `breakout_strength`: 直前5分間（判定時点の足を除く）の高値/安値に対する現在価格のブレイク幅（高値上抜け時は`price/high - 1`、安値下抜け時は`1 - price/low`、レンジ内は`0`）。Feature Engine（`featureengine.ComputeScreenSignals`）が算出する
  - `volatility_expansion`: `volatility_expansion_ratio`（`realized_vol_5m / realized_vol_15m`）。同上
  - 履歴不足で算出できない項は0ではなく欠損として合計から除外する（FR-FE-2と同じ扱い）

- FR-FS-3: フィルター設定値・スコア重みはすべてDB（Settings画面）で変更可能とする。優先順位は`config/strategy.yaml` < DB `runtime_settings`の`screener.*`キー（候補更新周期ごとに読み込むため再起動不要。キー一覧は`architecture/er.md` §runtime_settings）。`runtime_settings`の値はSettings画面（`/settings`の「運用設定」> Fast Screener。`internal/service/opsettings`・`POST`/`DELETE /ops-settings/:key`）から項目ごとに保存・「既定に戻す」（行の削除＝yaml値へ復帰）ができ、保存時に下記FR-FS-4と同じ検証（`config.ValidateFastScreenerOverrides`）を通らない値は400で拒否する。環境変数`PITHA_FAST_SCREENER_*`による上書き層は廃止した（issue #708）
- FR-FS-4（起動時検証）: `config/strategy.yaml`の`fast_screener.*`は、`scan.*`（既定値補完。FR-SCAN-1/FR-SCAN-2）と異なり**補完せず検証する**。`min_price`・`max_price`・`min_turnover_5m_jpy`・`max_spread_bps`・`min_volume_ratio`・`min_abs_return_5m_pct`・`min_realized_volatility`は0より大、`max_price >= min_price`、`top_n >= 1`（0は全銘柄が`top_n_cutoff`で除外されJev Scoutが一度も走らない、負数は上位N件の切り出しで範囲外参照になるため不可）、`weights.*`は0以上かつ少なくとも1つは0より大。キー欠落・タイプミスは0として読み込まれるため、未設定も違反として検出される。違反は項目名（例: `fast_screener.top_n`）付きで全件まとめて報告し、起動に失敗する。環境変数による上書き層は無い（issue #708）ため、検証対象は`config/strategy.yaml`の値で、`runtime_settings`上書きは保存時と候補更新時に別途検証する（下記）。`screener.Screen`は防御として`top_n <= 0`でも候補0件を返し、パニックしない（DB `runtime_settings`の`screener.top_n`のような実行時上書き経路向け） 同じ不変条件はDBの`runtime_settings`の`screener.*`上書き（FR-FS-3の最上位層）にも適用する: 候補更新（`internal/bootstrap/candidates`の`fastScreenerConfig`）は上書きが1件でもあれば全キー適用後に検証し（`config.ValidateFastScreenerOverrides`）、違反時は項目名（例: `screener.top_n`）付きのエラーで`Refresh`を失敗させ、候補リストを不正値で更新しない（`screener.top_n=0`も同じ検証で拒否する）。

### 4.3 スキャン頻度・イベント駆動

| 対象 | 周期 |
|------|------|
| 全体スキャン | 60秒ごと（`scan.full_scan_enabled: true`のときのみ。**既定オフ**。既定ではランキング監視が毎分、監視銘柄だけを対象にする。FR-SCHED-7/9） |
| 候補銘柄更新 | 15〜30秒ごと |
| ポジション保有銘柄 | 5〜15秒ごと |

- 周期は`config/strategy.yaml`の`scan.full_scan_interval_seconds`（60。`scan.full_scan_enabled: true`のときだけ使う。既定のランキング監視の周期は60秒固定）/ `scan.candidate_refresh_interval_seconds_min`・`_max`（15・30）/ `scan.held_position_interval_seconds_min`・`_max`（5・15）/ `scan.jev_scout_min_interval_seconds`（60）で設定する（括弧内は同梱の既定値、単位は秒）。各値は正の整数で、`_max >= _min`であること。kabu情報API・銘柄登録APIのプロセス全体上限は`scan.kabu_info_api_max_per_second`（既定8、公式上限10。`non-functional.md` §2.3）。`scan.full_scan_enabled: true`のときの`stale_snapshot`（FR-SCAN-5/7）の閾値は`scan.full_scan_max_snapshot_age_seconds`（同梱620。全件REST1周`ceil(4000/上限)`秒＋次サイクル待ちと余裕`2×full_scan_interval_seconds`。ランキング監視では使わず3分固定）。設定ローダー（`internal/config/scan_defaults.go`）は、未設定または0以下のキー（`full_scan_max_snapshot_age_seconds`は上記の式で算出した値）を同梱既定値で補完し、`_max < _min`の`_max`を`_min`に引き上げ、`kabu_info_api_max_per_second`が10を超える場合は10に切り下げる。いずれも警告ログを出す。0のままだと候補更新が待機なしで回り、全体スキャンが`@every 0s`で登録されるため（ホットループ防止）

- FR-SCAN-1: 以下のいずれかを満たした銘柄は通常周期を待たず再評価する: 1分リターン急変、出来高急増、スプレッド急拡大、板インバランス急変、VWAPクロス、高値/安値ブレイク、約定フロー急変（直近2バーの`trade_flow_imbalance`の差の絶対値が`config/strategy.yaml`の`scan.event_trigger.trade_flow_imbalance_change_threshold`以上。どちらかが欠損の場合は無信号）、ニュースフラグ発生。前バー（`history[0]`）との比較で判定するスプレッド急拡大・板インバランス急変・VWAPクロス・約定フロー急変は、前バーが現在バーの90秒以内（FR-FE-5の`minRefTolerance`と同じ。`eventtrigger.MaxPrevGap`）かつ同一セッション（同一JST日の前場または後場。`marketcalendar.SameSession`）にある場合のみ評価し、前営業日の引け・昼休み前の前場最終バー・再起動/欠測をまたぐ場合は発火しない。VWAPクロスは両バーにVWAPがある（`vwap > 0`）場合のみ判定する。高値/安値ブレイクは現在バーと同一セッションの履歴バーだけを基準にし、同一セッションの履歴がなければ発火しない
- FR-SCAN-2（再評価抑制）: `abs(return_1m) < threshold AND abs(volume_ratio_5m) < threshold AND abs(spread_change) < threshold AND no_event` の場合はFR-SCAN-1の**イベント駆動の即時再評価をスキップ**し、APIコストとレイテンシを削減する。適用範囲は`internal/bootstrap/marketdatajob`の即時再評価経路（`eventtrigger.Detect`の`Signal.Triggered()`が偽なら`Scheduler.EnqueueEventReevaluation`が何も投入しない。対象は現在のFast Screener候補のみ）に限る。定期の候補更新サイクル（下記）は静穏判定を行わず、Fast Screener通過銘柄すべてを銘柄別の間引きだけでScoutへ投入する（静穏な銘柄も最大で`scan.jev_scout_min_interval_seconds`ごとに1回はJevで再評価され、判断の鮮度とRAG/Calibration用の判断履歴を保つ。コストの上限は間引きで担保する）
- 候補更新サイクル（15〜30秒周期）からの`jev-scout`ジョブ投入は銘柄ごとに間引く（非機能§2.1の上限「1分あたりN銘柄×2（Scout+Trader）」を担保する機構）: 同一銘柄に`pending`/`running`の`jev-scout`ジョブがある間、および同一銘柄の直近の`jev-scout`ジョブ完了（成功・失敗とも）から`scan.jev_scout_min_interval_seconds`（既定60秒）経過するまでは投入しない（`internal/bootstrap/candidates`の`scoutHeld`）。これにより同一銘柄のScoutは通常1分あたり1回まで（通過銘柄のTraderを含めてもN×2/分以内）。FR-SCAN-1のイベント発火による即時再評価（`Scheduler.EnqueueEventReevaluation`）はこの間隔の対象外で、通常周期を待たず投入される（ただしその`jev-scout`ジョブも上記の`pending`/`running`・直近完了の判定対象になるため、直後の候補更新サイクルでの重複投入は起きない）。ワーカーの完了書き込み失敗で`running`のまま残った孤児行は、`started_at`から固定10分超でSchedulerが`failed`へ回復する（1分ごと。`non-functional.md` §2.1）ため、その銘柄は回復後（失敗扱いの完了時刻から`scan.jev_scout_min_interval_seconds`経過後）に再び投入され、再起動まで保留され続けることはない
  - 各thresholdは`config/strategy.yaml`の`scan.event_trigger.*`（`return_1m_change_threshold` / `volume_ratio_change_threshold` / `spread_change_bps_threshold` / `orderbook_imbalance_change_threshold` / `trade_flow_imbalance_change_threshold`）で設定する。判定は`abs(値) >= threshold`で、`return_1m_change_threshold`は1分リターン(`return_1m`)の絶対値、`volume_ratio_change_threshold`は5分出来高比率(`volume_ratio_5m`)の絶対値（前バーとの差ではなく現在値の水準判定。`volume_ratio_5m`は通常1.0前後の比率のため既定2.0は「5分出来高が平均の2倍以上」を意味する）、`spread_change_bps_threshold` / `orderbook_imbalance_change_threshold` / `trade_flow_imbalance_change_threshold`は直近2バーの差の絶対値と比較する。したがって、thresholdが0以下だと全バーでFR-SCAN-1が発火しFR-SCAN-2が無効化される。キー欠落（新キー追加前の古い`strategy.yaml`等）や0以下の値は設定ローダー（`LoadStrategy` / `LoadStrategyBytes`）が同梱既定値（`config/strategy.yaml`の値）で補完し、警告ログを出す

### 4.4 Jev Scout

- FR-TRADER-1: Scout通過銘柄に対し以下を評価する（FR-SCOUT-1と同じく`POST /v1/systemone`、入力は`market`と`similar_past_cases`）: `direction`（`choice`型: LONG/SHORT/NONE）, `regime`（`choice`型: TREND/RANGE/BREAKOUT/CHAOTIC）, `entry_quality`（`choice`型: poor/fair/good/strong/exceptional）, `toxic_flow`（`noul`型）, `liquidity_stressed`（`noul`型）, `continuation_probability`（`noul`型）。`confidence`は`direction`回答の`confidence`を用いる。質問セットのバージョンは現行`trader-v3`

- FR-TRADER-4（メタラベリングの材料、issue #761・親 #752）: Jevの出力は価格の方向予測ではなく、一次シグナル（`direction`＝LONG/SHORT/NONE の候補側）と、その候補を入る/見送るかの判断材料として扱う。`entry_quality`・`toxic_flow`・`liquidity_stressed`・`continuation_probability`・`confidence`は`jev.Score`（`TraderResponse.Score()`・`jev.ScoreOf(JevDecision)`）として特徴量に取り出せる: 各成分は[0, 1]で、`entry_quality`はpoor〜exceptionalを0〜1の5段階に正規化し、`Value()`は`toxic_flow`・`liquidity_stressed`を反転した5成分の単純平均（大きいほど入る側）。応答の値が範囲外・`entry_quality`が未知、または判断行に欠損がある場合はスコアなし（0とは扱わない）。質問文・スキーマ・保存内容は変えず、`TraderQuestionVersion`は据え置く。FR-TRADER-2は不変で、スコアを実際の勝率とみなさない（実結果に基づく較正は二次モデルが行う）
- FR-META-1（メタラベリングの二次モデル、issue #758・親 #752）: 一次シグナル（Jevの`direction`）と二次モデル（take/skip。サイズ比は記録のみで発注数量には使わない、FR-META-3）は分離する（`internal/service/metalabel`。永続化・スケジューラに依存しない純粋なコア）。特徴量ベクトルは`ofi_short`/`ofi_mid`/`ofi_long`（FR-FE-6）・`microprice_dev_bps`・`spread_bps`・`return_1m`・`jev_score`（`jev.Score.Value()`、FR-TRADER-4）・`tdnet_score`の8個で、`Features.Vector`がこの順に返す。LONG/SHORTのどちらの候補かで向きが変わる5特徴量（OFI×3・microprice乖離・1分リターン）はSHORTで符号を反転し、1つのモデルで両側を扱う。1つでも欠損（nil）・非有限なら特徴量ベクトルを作らない。モデルはロジスティック回帰（標準化＋L2のバッチ勾配降下。LightGBMはGoでは重いため後続）で、学習ラベルは`net_return_bps > 0`（FR-CAL-2のトリプルバリア）。
- FR-META-2（較正とEV）: 学習は重みの当てはめ用と較正用の2つの標本集合（互いに素。呼び出し側が時系列で分ける）を受け取り、較正はPlatt（ロジットのシグモイド）またはisotonic（PAV）で行う。期待値は**較正後**の勝率`p`から`p × WinBps − (1 − p) × LossBps`（bps、コスト控除後。`WinBps`/`LossBps`は学習標本の勝ち・負けの`net_return_bps`平均）で求め、較正前の確率は使わない。モデルは`params_json`（係数・標準化・較正器・`WinBps`/`LossBps`）に保存され、`ParseModel`が`feature_names_json`の不一致・非activeの行・未対応のアルゴリズム・非有限や不整合なパラメータを拒否する。
- FR-META-3（take/skipとサイズ比（記録専用））: `Decide`は較正後EVが0を超え、かつ最低EV（`DecideConfig.MinEVBps`、既定0。Settingsの運用設定は issue #759）を超えるときだけ`take`し、サイズ比`SizeFraction`はKelly比`EV / WinBps`に`KellyFraction`（既定0.25）を掛けて1以下に丸めた値とする（`skip`は0）。**`SizeFraction`は記録専用で、発注数量には使わない**（issue #781の決定）: `metalabel_predictions.size_fraction`への保存とログ出力だけに使い、Paper Entryの数量はFR-ENTRY-3のRisk上限だけで決まる（`take`ならEVの大小に依らず同じ数量）。確率較正が現行版のPaper実績で検証できるまでこの方針で固定し、検証前に数量へ配線しない（Kelly比`EV / WinBps`はEVと勝ち幅`WinBps`の推定誤差に非常に敏感で、未検証の較正のままではEVの過大評価が過大な数量に直結するため）。再検討はissue #781で行い、その場合も上限付きのハーフケリー以下を前提とし、数量がRisk上限（FR-ENTRY-3）を超えない・上限値を設定に持つ・サイズ帯別の損益を確認できることを要件とする。したがってPaperの評価（EV・損益）はサイズ一定を前提とする。**安全側は見送り**: 有効モデル無し（nil）・モデルが壊れている・LONG/SHORT以外・特徴量の欠損・設定不正・予測の失敗はすべて`skip`で、`Decision.Reason`（`no_active_model`/`model_unusable`/`no_candidate`/`missing_feature`/`invalid_config`/`predict_failed`/`ev_not_above_minimum`）に理由を残し、エラーは返さない。結果は`metalabel_predictions`の行（`raw_probability`/`calibrated_probability`/`expected_value_bps`/`action`/`size_fraction`/`reason`/`features_json`）に対応する。
- FR-META-4（ウォークフォワード夜間再学習、issue #764・親 #752）: `training.Trainer`（`internal/service/metalabel/training`）が、`scheduler.WithMaintenanceTask`で登録される日次メンテナンスタスク`metalabel_retrain`（`internal/bootstrap/metalabeljob`。Settingsの再学習時刻前は`maintenance.ErrSkipped`で成功にも失敗にも数えない）（non-functional.md §3のcatch-up方式: 起動時と10分ごとに確認し、当日成功するまで実行、失敗は30分後に再試行、3回連続失敗で通知）として、Settingsの`metalabel.retrain_time`（JST）以降に1日1回、モデルを再学習して`metalabel_models`へバージョン（`lr-YYYYMMDD-HHMMSS`）・窓・OOS指標（AUC、OOS上でDecideが採ったシグナルの平均純リターン=EV、較正曲線）とともに保存する。学習データは`calibration_outcomes`のトリプルバリアラベル（`label_version=2`、コスト控除後`net_return_bps`）に紐づくLONG/SHORTのTrader判断で、特徴量は判断時点のもの（OFI列・`state_json`の`spread_bps`/`return_1m`・Jevの回答のスコア・`state_json`の`news_context`から`newsfeed.ScoreNewsContext`で再計算したTDnetスコア。欠損のある判断は捏造せず除外しログに件数を出す）。**情報リーク防止**: 時系列で 学習(fit) < 較正 < OOS に分け、各区間の境界で、ラベル窓（判断時刻＋バリアのtimeout）が次区間の開始の`Embargo`（既定30分）手前以降に届く行を除外（purge+embargo。除外件数はログに出す）し、ラベルが未確定の行（ラベル窓の終了が現在より後）は使わない。`oos_start`は`train_end`＋embargo以降になる。**LLMのlook-ahead bias対策（arXiv:2512.23847）**: OOS窓は`[max(now-7日, metalabel.llm_cutoff), now)`で、Jevの特徴量を使う評価はLLMの学習データcutoff以降の判断だけで行う。評価期間・cutoff・各標本数・purge件数は毎回ログ（`metalabel: walk-forward windows`）に出し、`metalabel_models.oos_start/oos_end`にも保存する。**採用基準**: OOS件数・take件数・取引日数が最小値以上で、EV・AUCの信頼区間の下限が基準を超え、現行モデルを悪化させず、変更頻度制限に掛からないときだけ`active`、満たさなければ`rejected`＋`reject_reason`（基準値・理由コードは**FR-META-7**。仮置きのLLM cutoffでの不採用はFR-META-6）で記録のみ（推論は`LatestActiveModel`しか使わないので既存モデルのまま）。**学習に失敗しても安全側**: 設定不正・DB/保存失敗・学習失敗はエラーとして何も保存せず既存モデルを維持し、履歴が足りない/片側のみ（`ErrInsufficientData`）は警告ログで見送る（モデルが無ければ推論は`skip`のまま）。

- FR-META-6（LLM学習データ終了日の扱い・仮置き時の不採用・出典記録、issue #776・親 #752）: メタモデルのOOS評価は、Jev（LLM）が結果を既に知っている期間を含むと過大評価される（look-ahead bias、arXiv:2512.23847）。そのためOOS窓は`[max(now−7日, metalabel.llm_cutoff), now)`とし（FR-META-4）、cutoffを次の3状態に分類する（`metalabelsettings.Settings.CutoffStatus`）: **`placeholder`**=未設定または既定の仮置き値`2026-01-01`（`DefaultLLMCutoff`）のまま、**`unverified`**=実日付だが確認したJevモデル名（`metalabel.llm_cutoff_model`）が未記録、**`confirmed`**=実日付かつモデル名記録済み。
  - 仮置き（`placeholder`）のまま: 仮置き日付は本アプリの記録開始（2026-09-26）より前で除外が事実上働かず、OOSが学習期間と重なり得るため、**採用不可**とする（推奨の(a)警告＋(b)不採用を採る）。夜間再学習は通常どおり学習・評価して`metalabel_models`へ保存するが、OOS指標が基準を満たしても`status=rejected`・`reject_reason=llm_cutoff_placeholder`とし、有効な既存モデルがあってもそれを更新も置換もしない（`LatestActiveModel`は既存モデルのまま。既存モデルが無ければ見送り＝FR-META-3の安全側）。夜間再学習のログに毎回WARN（`metalabel: LLM cutoff is not confirmed`、`cutoff_status`・`llm_cutoff`付き）を出し、Settings画面のcutoff行とCalibration画面（`meta_model_cutoff.warning`）に警告を表示する。実日付を保存すると警告は消え、OOS開始は`max(now−7日, cutoff)`になる。
  - Jevのモデル切替: `metalabel.llm_cutoff_model`が記録済みで、OOS窓の判断（`jev_decisions.model_id`）にそれと異なるモデルが含まれるとき、cutoffは応答しているモデルの学習データ終了日ではないため、`status=rejected`・`reject_reason=llm_model_changed`とし、新モデルのcutoffを再確認して`metalabel.llm_cutoff_model`を更新するまで採用しない（ログに該当モデル名を出す）。モデル名が未記録（`unverified`）のときは切替を検知できないため、**Paperでは警告のまま採用できる**（日付だけ設定した運用を妨げない）が、**Live前チェックでは採用を止める**（`status=rejected`・`reject_reason=llm_cutoff_unverified`。`training.WithMode(metalabelsettings.ModeLive)`で判定する。issue #780の決定・2026-10-19。Paperは既定の`metalabelsettings.RuntimeMode`（本ビルドでは`ModePaper`）で、夜間再学習の挙動は変えない）。止めても有効な既存モデルは更新されない。**現状Liveの起動経路は無く（#55 blocked）、本番コードで`ModeLive`を渡す箇所は未配線**で、判定の実体は`cutoffGate`とそのテストにある。Settings画面の「Live 前チェック」パネル（日次ルール、FR-SETTINGS・issue #782。警告のみ）とは別のもので、そちらは変えない。
  - 出典の記録: `metalabel.llm_cutoff_model`（確認したJevモデル名、`jev_decisions.model_id`と同じ表記）・`metalabel.llm_cutoff_confirmed_on`（確認日`YYYY-MM-DD`）・`metalabel.llm_cutoff_source`（出典。200文字以内）を`runtime_settings`に保存する（FR-SETTINGS-7。既定は空＝未記録、環境変数は無し）。Calibration画面に出典を表示する。実際のJevモデルの学習データ終了日・出典は運用者が公式情報で確認して設定する（リポジトリからは不明。確認前は`placeholder`のため採用されない）。Settingsの「メタラベリング」グループ上部に「LLM cutoffの状態と確認手順」パネルを出し、状態（仮置き`placeholder`／未確認`unverified`／確認済み`confirmed`。`CutoffStatus`と同じ分類）・記録済みの日付・モデル名・確認日・出典（未記録は「未記録」）と、公式日付の確認手順の短いヘルプ（どこを見るか＝使用中のJevモデルのベンダー公式モデルカード／ドキュメントのknowledge cutoff、各キーに何を入れるか＝`llm_cutoff`はYYYY-MM-DD・`_model`は確認したモデル名・`_confirmed_on`は確認日・`_source`はURLか文書名）を表示する。保存のたびにパネルは更新され、日付とモデル名を記録して`confirmed`になると、仮置きの状態表示と警告は消える。MCPの`settings_get`は同じ状態を固定コード`llm_cutoff_status`で返し、あいりは`settings_set`だけで日付と出典4キーを更新できる（FR-MCP-22、issue #809）。この更新で採用判定は変わらず、Live前の`unverified`不採用（issue #780）も維持する。
  - fit／較正データの扱い（決定と影響評価）: cutoffで絞るのはOOS窓だけで、fit・較正の行はcutoff前のものを含めて使う（行の絞り込みはしない）。影響: (1) cutoff前の判断ではJevが結果を知っていた可能性があり、`jev_score`特徴量の係数が過大に学習され、較正後の確率が楽観側にずれ得る。(2) ただし採否は**cutoff以降のOOS**の実リターンで判定するため、このバイアスは採用判断を甘くしない（楽観的な確率は、OOSでの較正曲線・EVの悪化として現れ、不採用側に働く）。(3) 絞ると、記録開始（2026-09-26）以降の少ないデータからさらに学習量が減り、最小標本（fit 100・較正 30）を満たせなくなる。以上より当面は絞らず、各夜のログに`fit_before_llm_cutoff`（cutoff前のfit・較正行数）を出して影響を監視する。cutoff以降の行だけで最小標本を満たせる量が貯まった時点で、cutoff前の行を除いて学習する方針へ切り替えを検討する（未実装・要判断）。RAGの類似過去局面は実結果を含む（FR-RAG-3）ため、OOSの独立性はFR-RAG-4の除外（同一銘柄の直近15分）以上には保証しない。
- FR-META-7（採用基準・多重検定対策・変更頻度制限・前向き評価、issue #780・親 #752）: 夜間再学習のモデルは、OOSの点推定ではなく**信頼区間**で採用を判定し、毎晩の再学習で偶然良く見えたモデルが入れ替わるのを防ぐ（`training.AcceptanceConfig`・`changeguard`）。判定は次の順で、最初に満たさない条件の理由を`reject_reason`に記録して**不採用**（モデルは`rejected`で保存、有効な既存モデルは更新しない）とする。サンプルが足りない日は不採用が既定。
  - (1) 最小サンプル（既定値）: OOS件数 **1084** 以上・take件数 **542** 以上・OOSが跨ぐ取引日（JST）**5** 日以上（`oos_samples_below_minimum`/`oos_takes_below_minimum`/`oos_days_below_minimum`）。(2) EVとAUCの信頼区間: 1 takeあたり純EVの信頼区間の**下限が0超**（`oos_ev_ci_not_positive`）、AUCの信頼区間の**下限が0.5超**（`oos_auc_ci_not_above_minimum`）。区間は、同日・同銘柄の判断が同じ値動きと相場環境を共有する相関を考慮した**クラスタ・ブートストラップ**（日を復元抽出し、選んだ日の中で（日, 銘柄）クラスタを復元抽出する二段階。乱数は`math/rand/v2`のPCGで、シードは学習時刻から決め`adoption_json`に保存して再現できる）の**2000**回・両側98%（片側1%）パーセンタイル区間とする（`training.DefaultResamples`・`DefaultAlpha`）。(3) 現行モデルとの比較（下記）。(4) 変更頻度制限（下記）。
  - 必要件数の逆算（根拠）: EVの片側検定（水準α=1%）で、1 takeの純リターンの標準偏差を**σ=30** bps（トリプルバリアの既定TP/SL=30bpsで1件の結果が±30bps付近に分布するため。`barriersettings.Default`）、採用に値する想定エッジを**5 bps**/take（σの約1/6。コスト控除後）、**検出力80%**として、必要な独立take数は n = ((z₁₋α + z₈₀%)·σ/δ)² = ((2.326 + 0.842) × 30 / 5)² ≈ 361。同日・同銘柄の相関によるデザイン効果を1.5（1 + (m−1)ρ。ρ≈0.09、1クラスタ約6判断）と見て**take 542 件**（`training.RequiredTakes`）。takeはOOSの約50%と見て**OOS 1084 件**、区間の再抽出単位（日）が少なすぎると区間が不安定になるため**5営業日**（最小値）。以前の基準（OOS 30・take 10・AUC>0.5・EV>0の点推定）はこの逆算で必要な件数の約1/36（OOS件数）〜1/54（take件数）で、偶然でも満たし得た。想定値（σ・エッジ・検出力・デザイン効果・take率）は`training`の定数（`AssumedSigmaBps`等）で、実運用のペーパー結果が貯まったら見直す（現状の実測分布は未確認）。コードの既定値と本節の数値の一致は`TestDefaultAcceptanceConfig_MatchesTheSpec`が検査する。
  - 偽採用率の上限（5%）: 効果の無い合成データ（結果が特徴量と無関係な±30bpsのコイン投げ＋強い日次の共通ずれ（勝率のsd 12%））で学習・判定を再現可能な乱数で繰り返し、採用される割合が**5%以下**であることを`TestAdoption_FalseAdoptionRateOnNoiseIsWithinTheBound`が検査する。区間単体の誤判定率は、最小の5日・日次の共通ずれsd 15%（日次のEV差が約9bps）のもとで下限が0を超える割合が5%以下であること（同じデータを判断ごと独立として扱う通常のブートストラップでは約18〜30%に達すること）を`TestEVInterval_CoversTheNullUnderSameDayCorrelation`が検査する。α=2.5%では5日・強い日次相関で5%を超えるため片側1%とした。

  - ホールドアウトと前向き評価: 採用判断に使ったのはOOS窓（採用時点までの判断）だけで、採用後に生じた判断（`decided_at >= trained_at`、ラベル確定済み）は採用判断に一度も使っていない。夜間再学習は、学習の成否にかかわらず、現行の有効モデルをその判断だけで評価し（`training.EvaluateForward`。採用基準とは別の指標）、件数・take数・営業日数・EVとその信頼区間を`metalabel_models.forward_json`に更新する。EV区間の**上限が0未満**なら`degraded`としてWARNログと画面の警告を出す（モデルの状態は自動では変えない。基準は次の夜間再学習の比較と、運用者の判断）。

- FR-REGIME-1（相場状態判定とモメンタム／VWAP回帰の切替、issue #755・親 #751）: 候補はkabuの`/ranking`（値上がり率・出来高急増など）から来てモメンタムを後追いする構成のため、相場がレンジ（平均回帰）のときの順張りは逆張りより成績が悪い。そこでJev Traderを呼ぶ前に**相場状態（レジーム）**を判定する（`internal/service/regime.Assessor`、`policy.WithRegimeAssessor`）。判定は追跡中の市場指数（`instruments.kind = market_index`。FR-FE-4と同じ銘柄。複数あれば平均）の1分足リターンを使う: 窓（Settings `regime.window_minutes`、既定30分）内の1分足リターンの標準偏差（ボラティリティ、bps）と1次自己相関で、ボラティリティが下限（`regime.min_volatility_bps`、既定0.5）以上のとき、自己相関が`regime.autocorr_threshold`（既定0.2）以上なら`trend`、−しきい値以下なら`mean_revert`、その間・指数データ不足・静かな相場は`unknown`とする。1分足は分ごとの最後の足で作り、欠けた分をまたぐリターンは作らない。判断時点以降の足は使わない（FR-FE-1）。指数の足が`MarketContextMaxAge`より古ければ`unknown`。判定は判断ごとに`jev_decisions`の`market_regime`/`ab_arm`/`regime_volatility_bps`/`regime_autocorr`/`vwap_z`へ保存する（Jevには送らず`state_hash`にも含めない）。レジームに応じた戦略: `trend`・`unknown`は既存のモメンタム追随（Jevの`direction`とFR-POLICY-6のメタモデル判定）。`mean_revert`では**VWAP回帰モード**に切り替え、銘柄の寄り付き以降のVWAP乖離zスコア（最新の足の`price_vs_vwap_bps`÷寄り付き以降の足のその二乗平均平方根。`featureengine`の`PriceVsVWAPBps`を再利用し、`vwapcross`が見る「VWAPからの乖離」を標準化したもの）の絶対値が`regime.vwap_z_threshold`（既定2）以上のとき、**VWAPへの戻りを狙って逆張り**する（VWAPより上＝SHORT、下＝LONG。Jevの`direction`は問わず、`direction=NONE`でも候補が出る）。zが算出できない（寄り付き以降の足が10本未満など）ときは`vwap_z_unavailable`、しきい値の内側は`vwap_not_extreme`のNONE。回帰側はJevのモメンタム方向ではないため`entry_quality`・`continuation_probability`は見ず、`toxic_flow`・`liquidity_stressed`のハードガードと貸借なしショートの拒否、FR-POLICY-3のスプレッド/流動性/特別気配/ストップ高安の判定、メタモデルの較正後EV判定（FR-POLICY-6）、Risk Engineは通常どおり通す。**paperのA/B比較**: Settings `regime.ab_enabled`（既定0=無効）が1のとき、判断を銘柄と足の時刻から決定的・ほぼ均等に`momentum`（固定モメンタム）と`regime`（レジーム切替）の2アームへ振り分ける（再実行で同じアームになる）。VWAP回帰が使われるのは`regime`アームの`mean_revert`だけで、他は両アームとも同じモメンタム追随。無効のあいだは全判断が`momentum`アーム。アーム別・レジーム別のコスト控除後EV（`realized_pnl`÷建玉額の平均、bps）・勝率・件数・損益は`GET /api/v1/calibration`の`ab_arms`とキャリブレーション画面に表示する（FR-CAL-2）。バックテスト（`internal/service/backtest`）は保存済みの判断のレジームでリプレイし、トレードにレジームとアームを付けて`Result.ByRegime`にレジーム別の指標を返す。窓幅・自己相関しきい値・ボラティリティ下限・zしきい値・A/B有効はSettingsの運用設定（FR-SETTINGS-7）で、環境変数・yamlでは設定しない。liveは#55がblockedのまま、paperのみ

### 4.7 Risk Engine

Risk EngineはJevより優先され、Jevから変更できない。Phase 7（実売買）移行後も人手承認を挟まず自動運用することを前提とし、その代わりPaper運用よりも厳格なLive用リミットと、後述のdead-man's switchで安全側に倒す。

| 項目 | Paper初期値 | Live初期値（Phase 7） |
|------|-----------|----------------------|
| max_position_per_symbol_pct | 100.0（issue #804。Settingsで変更可。変更前は2.0） | 1.0 |
| max_total_exposure_pct | 100.0（issue #804。Settingsで変更可。変更前は20.0） | 10.0 |
| max_daily_loss_pct | 1.0 | 0.5 |
| max_trade_loss_pct | 1.0（issue #804。Settingsで変更可、0.1〜3.0。変更前は0.25） | 0.15 |
| max_open_positions | 5 | 3 |
| max_same_direction_positions | 3 | 2 |
| market_adverse_return_5m_pct | 0.2 | 0.15 |
| max_spread_bps | 30 | 20 |
| max_consecutive_losses | 4 | 3 |
| cooldown_after_loss_minutes | 5 | 10 |
| force_flat_before_market_close_minutes | 10 | 15 |
| heartbeat_timeout_minutes（Live専用） | 対象外 | 120 |

- FR-RISK-1: 上記制限のいずれかに抵触する場合、新規取引を拒否する
  - 「口座資産に対する%」の各上限（max_position_per_symbol_pct / max_total_exposure_pct / max_daily_loss_pct / max_trade_loss_pct）の分母は`config/risk.yaml`の`initial_capital`（想定資金・円。Paper初期値50万円（issue #804。Settingsで変更可、FR-RISK-9）、Liveは実運用資金を設定必須）とする。総エクスポージャ・銘柄エクスポージャは保有中ポジションの評価額（数量×現在値）、日次損失率は当日（JST）にクローズしたポジションの実現損益と保有中ポジションの含み損益の合計損失を分母で割った値
  - `initial_capital`が未設定（0以下）、またはRisk Engineが判定に必要な状態（ポジション・注文・最新スナップショット・スプレッド）を読み取れない場合は、判定をスキップせず`risk_engine_error`で拒否する（fail-closed。スプレッド欠損は「データ欠損」、FR-POLICY-3）
  - 同じ方向に重ねない制約（相関・市場逆行）: モメンタム・出来高急増・ブレイクアウトは同じ地合いで同じ方向の銘柄に寄るため、銘柄ごとの上限だけでは相場要因でまとめて負けるのを防げない。Risk Engineは新規エントリーの方向（LONG/SHORT）と同じ向きの保有ポジション数を読み、(1)`max_same_direction_positions`以上なら`max_same_direction_positions`理由で拒否する（反対方向の保有は数えない）、(2)同方向を1件以上保有中に、市場全体が保有方向と逆行している（`market_adverse_return_5m_pct`（%）以上、LONGなら下落・SHORTなら上昇）なら`market_adverse_to_direction`理由で拒否する。市場全体の動きは既存の`market_return_5m`（`kind=market_index`の追跡銘柄、TOPIX等。§4.1 FR-FE-4）を使い、先物専用の新規データ取得は要しない。`market_return_5m`が算出不能（指標未追跡・足の欠損）の場合、または同方向の保有が無い場合は市場逆行では拒否しない（相関はポジション間の重なりを抑える制約のため）。判定は最新スナップショット（`market_snapshots`）の値で行い、拒否理由はスプレッド等と同じく`trade_signals.reject_reason`に`risk_engine_rejected: <理由>`（例: `risk_engine_rejected: market_adverse_to_direction`。理由が空なら`risk_engine_rejected`のみ）として記録される
  - `max_trade_loss_pct`はポジションサイジングで強制する（§4.8 FR-ENTRY-3）。1単元（100株）でもStop Lossに掛かった時の損失が上限を超える場合は`max_trade_loss_pct`理由で拒否する
  - `config/risk.yaml`の各上限は起動時（`LoadRisk`/`LoadRiskBytes`）に検証し、範囲外の項目があれば項目名（例: `paper.max_daily_loss_pct`）を含むエラーで起動を失敗させる（違反は全件まとめて報告する）。`risk.yaml`/`strategy.yaml`は未知のキーをキー名付きエラーとして拒否する（strict decode）。キーの欠落は0として読み込まれ、`max_daily_loss_pct`=0・`max_consecutive_losses`=0は損失も連敗も無い状態でKill Switchを発動し続けるため（手動再開しても1分周期の判定で即再発動する）、「上限なし」の意味では扱わない。`max_position_per_symbol_pct`/`max_total_exposure_pct`/`max_daily_loss_pct`/`max_trade_loss_pct`/`max_spread_bps`/`market_adverse_return_5m_pct`は正（>0）、`max_open_positions`/`max_same_direction_positions`/`max_consecutive_losses`は1以上、`cooldown_after_loss_minutes`/`force_flat_before_market_close_minutes`は0以上、`heartbeat_timeout_minutes`はPaperは0以上・Liveは1以上（0・欠落ではFR-RISK-6のデッドマンスイッチが無警告で無効化されるため）。`initial_capital`はこの検証の対象外（上記の未設定扱い）。Paperは常に検証し、Liveは`live`セクションに1つでも値が定義されている場合のみ検証する（`live`セクションが無い場合はLive未運用として未検証）
- FR-RISK-2: 以下のいずれかでKill Switch（新規取引停止）を発動する: 日次損失上限到達、連敗上限到達、市場データ停止、Jev API連続失敗、Broker API異常、想定外ポジション発生、約定差異検知、DB書き込み失敗が一定回数継続、operator_heartbeat_timeout（Live専用、FR-RISK-6参照）、オペレーターによる手動Kill（`POST /api/v1/system/kill`。reason=`operator_manual`）
- FR-RISK-3: Kill Switch発動時、必要に応じて保有ポジションをクローズする（強制決済の対象reasonは`architecture/overview/flows.md` §10.3。強制決済は通知（Wails・Slack）より先に実行し、Slackの遅延・不達で決済を遅らせない。通知は決済が失敗しても試行し、通知失敗はログのみ。オペレーターの手動Killも UC-11 の「強制決済」として全ポジションをクローズする）
- FR-RISK-4: Kill SwitchはUI（Wailsアプリ）とサーバー内部処理の両方から操作可能とする。Phase 7の発注確定・Kill Switch操作に人手の追加認証は要求しない（完全自動運用）
- FR-RISK-5: Kill Switch発動・自動再開・解除を監査ログ（`kill_switch_events`・`kill_switch_resolutions`、追記専用）に記録する。通常のRisk拒否（`max_open_positions`・`max_total_exposure_pct`・`max_spread_bps`・`market_adverse_to_direction`・`max_trade_loss_pct`・`cooldown_after_loss`等、FR-RISK-1）は`Engine.Check`が`(false, reason)`を返すだけで`kill_switch_events`には書かず、理由を`trade_signals.reject_reason`（Policy Engineが保存）とslogに残す。手動Killは`operator_manual`として`kill_switch_events`に、手動Resumeによる解除は`resolved_by=manual`として`kill_switch_resolutions`に残る（Kill Switchを伴わない手動Pause/Resumeはslogの監査行`risk: audit: manual pause|resume`に記録する）
- FR-RISK-6（dead-man's switch、Live専用）: Wailsアプリの認証済みUIリクエストを「操作者ハートビート」として記録する。立会時間中に`heartbeat_timeout_minutes`（初期値120分）を超えてハートビートが途絶した場合（最後のハートビートがその営業日の寄り付き前なら、寄り付き（9:00 JST）からの経過時間で判定する。立会時間外（昼休みを含む）は判定しない）、Risk Engineは自動的に新規エントリーを停止する（保有ポジションのExitルールは継続）。オペレーターがUIを再度操作した時点でこの停止理由は自動解消する（解消判定は「発動時刻より後の本物のハートビートが記録され、かつそれが`heartbeat_timeout_minutes`以内」であること。発動判定用の寄り付きクランプは解消判定には使わず、寄り付き前の時間帯でも操作者不在のまま自動解消しない）。画面が自動で発火する再同期・ポーリング・WebSocket再接続はオペレーターの操作ではないためハートビートに数えない（`architecture/overview/flows.md` §10.4）
- FR-RISK-7（Kill Switch再開の自動/手動分類）: `kill_switch_events.reason`により再開方法を分ける

| 発動理由 | 再開方法 |
|---------|---------|
| market_data_down（データ復旧確認後） | 自動再開 |
| jev_api_down（API復旧確認後） | 自動再開 |
| operator_heartbeat_timeout（ハートビート再検知） | 自動再開 |
| daily_loss_limit（日次損失上限到達） | 手動再開のみ |
| unexpected_position（想定外ポジション） | 手動再開のみ |
| fill_discrepancy（約定差異） | 手動再開のみ |
| consecutive_losses（連敗上限到達） | 手動再開のみ |
| db_write_failure（DB書き込み失敗継続） | 手動再開のみ |
| broker_api_error（Broker API異常） | 手動再開のみ |

`cooldown_after_loss`（連敗後クールダウン）は`kill_switch_events`に記録しない時間ベースの新規取引ゲート（FR-RISK-1）であり、本表の対象外（下記判定基準を参照）。

- 再開ベースライン（FR-RISK-2/FR-RISK-7）: `consecutive_losses`・`daily_loss_limit`は手動再開のみだが、発動の原因となったクローズ済みポジションは履歴に残り続ける。再開直後に同じ履歴で再発動して復帰不能になるのを防ぐため、手動Resumeがこれらのイベントを解除した時刻を`runtime_settings`にベースラインとして記録する（`system.loss_streak_baseline_at`・`system.daily_loss_baseline_at`）。`fill_discrepancy`のResumeも同様に`system.fill_discrepancy_baseline_at`を記録し、逆方向の孤児約定照合はResume時刻より前にFILLEDとなった注文を対象外とする（直近15分の照合窓内の同じ孤児注文で再発動して再度全ポジションを強制決済するのを防ぐ。ポジション起点の突合は対象外）。以後、連敗数・クールダウン起点（`cooldown_after_loss`）はベースライン以降にクローズしたポジションのみ、日次損失率の実現損益もベースライン以降にクローズした分のみを対象とする（保有中ポジションの含み損は常に算入するため、実際に損失が拡大すれば再発動する）。2つのベースラインは独立で、連敗Resumeは当日の実現損失を帳消しにせず、日次損失Resumeは連敗数をリセットしない。手動Kill・Pauseなど他理由のResumeはどちらも動かさない。ベースラインより後に上限回数の敗北（連敗）または上限を超える損失（日次）が再び発生した場合のみ再発動する。連敗数は営業日をまたいで持ち越す（日次リセットしない）が、Resumeでリセットされる。

FR-RISK-2/FR-RISK-7の検知・自動再開は、Schedulerが1分周期で実行する（`internal/service/scheduler`の`WithRiskMonitor`/`WithAutoResumer`）。判定基準は以下。

- market_data_down: kabuステーションAPIの板取得（`GetBoard`）が5回連続で失敗（成功1回で復旧、自動再開）。数えるのはフィード側の失敗（トークン未保持・通信エラー・HTTP 5xx・認証/トークン系の4xx＝401/403と`4001007`/`4001008`/`4001009`/`4001013`/`4001017`）のみ。銘柄単位の4xx（`4002001`銘柄が見つからない、廃止・停止銘柄など）と429/`4001006`は数えず、当該銘柄をstaleにするだけ（無効銘柄が並んでも全体停止にしない。issue #532）
- jev_api_down: Jev APIの直近呼び出しエラー率がしきい値（既定50%、直近20件、最小5件）以上（しきい値未満に戻るか、5分間呼び出しが無ければ復旧、自動再開。復旧後の最初の呼び出しは古い失敗窓を破棄して新しい窓で評価し、窓が最小5件に達しエラー率がしきい値以上になるまで再発動しない）。Slack通知（§5.2）と同じ信号を使う
- broker_api_error: kabuステーションAPIがHTTP 5xxを5回連続で返す（手動再開のみ）。4xx・通信エラーは対象外（通信エラーは市場データ停止側で扱う）
- db_write_failure: SQLiteの書き込みがストレージ起因（BUSY/LOCKED/READONLY/IOERR/FULL/CANTOPEN/CORRUPT/NOTADB。NOTADBはDBファイルがSQLite形式でない状態で、破損の一種として扱う）で5回連続失敗（手動再開のみ）。制約違反は対象外。書き込みはExec系に加え、トランザクションの`BEGIN`（`_txlock=immediate`の書き込みロック取得失敗）と、読み取り専用でないトランザクションの`COMMIT`の成否も計上する。`RETURNING`付きクエリ（孤児ジョブ回復`FailOrphanedRunning`のみ）は計上対象外
- unexpected_position / fill_discrepancy: Paper Tradingでは外部Brokerが無いため、保有中ポジションを起点となる`paper_orders`の約定記録と突合する。起点注文が存在しない・未約定・銘柄/売買方向が不一致なら`unexpected_position`、約定数量・約定価格がポジションと不一致、または指値を超えた約定なら`fill_discrepancy`（手動再開のみ）。逆方向の照合として、直近15分内（約定直後の1分は猶予）にFILLEDとなった注文がどのポジションのEntry/Exit注文にもなっていない場合も`fill_discrepancy`とする
- cooldown_after_loss: クールダウンはRisk Engineの時間ベースの新規取引ゲート（FR-RISK-1、`kill_switch_events`には記録しない）であり、経過で自動的に解除される
- daily_loss_limit / consecutive_losses: 新規シグナルに対するRisk Engineの判定（`Check`）に加え、この1分周期の検知でも同じ判定（再開ベースライン考慮）を行う。シグナルが出なくても、日次損失（含み損込み）が上限に達した、または連敗上限に達した時点でKill Switchの発動・通知・保有ポジション強制決済（FR-RISK-3）を行う（手動再開のみ）
- 強制決済の再試行: 強制決済対象reason（`architecture/overview/flows.md` §10.3）のKill Switchが未解除のまま保有ポジションが残っている場合、同じ1分周期で全ポジションの強制決済を再実行する（発動時の一度きりの決済が一時的に失敗しても、Killed状態のまま建玉が残り続けないようにする。決済は冪等）

### 4.8 Entry / Exit

- FR-ENTRY-1: 成行想定Paper Entry・指値Paper Entryの両方を選択可能とする。現状はExecutionエンジン（`internal/service/execution`）が両方を実装しており（`EntryRequest.OrderType`/`LimitPrice`、`Config.PreferLimit`、PENDING指値の約定処理`TryFillPending`）、本番経路（Policy → `paperexec` → Execution）は`OrderType`/`LimitPrice`を指定しないため常に成行想定で発注する。`Config.PreferLimit`は`config/*.yaml`・環境変数・`runtime_settings`のいずれにも設定キーが無く既定のfalse（成行）固定であり、運用で指値Entryを選ぶ手段は未提供（本番経路への配線は実売買移行時にFR-ENTRY-2と併せて行う）
- FR-ENTRY-2: 実売買へ移行する場合は原則として指値を優先する（Paper Tradingの現行運用は上記のとおり成行想定）
- FR-ENTRY-3（ポジションサイジング）: Paper Entryの発注数量は、次の3つの上限株数の最小値を単元（100株）単位に切り下げた値とする。1単元にも満たない場合は発注せず、拘束した制限（`max_trade_loss_pct` / `max_position_per_symbol_pct` / `max_total_exposure_pct`）を理由に見送る
  - 1トレード最大損失: `initial_capital × max_trade_loss_pct ÷ (価格 × stop_loss_pct)`
  - 銘柄上限: `initial_capital × max_position_per_symbol_pct ÷ 価格`
  - 総エクスポージャ残枠: `initial_capital × (max_total_exposure_pct − 現在の総エクスポージャ率) ÷ 価格`
  - `GET /api/v1/symbols/{symbol}`の`risk.allowed_position_pct`は、直近価格で同サイジングを行った結果の数量が占める`initial_capital`比（%、発注不可なら0）
  - メタモデルのサイズ比`SizeFraction`（FR-META-3）は数量の計算に使わない（issue #781の決定。確率較正がPaper実績で検証されるまで固定）。数量は上記3つの上限だけで決まり、`take`したシグナルはEVの大小に依らず同じ数量になる。Paperの評価（EV・損益）はこのサイズ一定を前提とする
- FR-ENTRY-4（約定の原子性）: Entry注文の約定（`paper_orders`のFILLED化）とポジション作成（`positions`）は単一のDBトランザクションで行う。失敗時は注文をFILLEDにせず、約定済み注文がどのポジションにも紐付かない状態（孤児約定）はRisk Engineの照合が`fill_discrepancy`として検知する（§4.7）
- FR-ENTRY-5（銘柄単位のEntryゲート）: Executionエンジンの`Enter`は、次のいずれかに該当する銘柄への新規Entryを受け付けない（`ErrOutsideTradingSession` / `ErrPositionAlreadyOpen` / `ErrPendingOrderExists` / `ErrSymbolInCooldown`）。Risk Engineの判定（FR-RISK-1）とは別の、Execution自身の不変条件である
  - 立会時間外、または引け前強制決済の開始時刻以降（Calendar設定時。直ちに強制決済されるEntryを避ける）
  - 保有中のポジションがある（`positions`の部分UNIQUEインデックス、`architecture/er/tables-trading.md`。同一銘柄の同時ポジションは1つ）
  - 未約定（PENDING）のEntry注文がある（先の注文でポジションができると2本目は約定し得ないため、重複させない）
    - 成行注文は発注直後に約定するため、1分以上PENDINGのまま残った成行注文（INSERTと約定の間のクラッシュ等による孤児）はゲートせず、`Enter`/`OnSnapshot`がREJECTEDへ遷移させる（指値注文の重複拒否は従来どおり）。約定失敗時のREJECTEDはctxキャンセルと切り離して実行する
  - その銘柄で損失クローズ（実現損益<0）した時刻から`cooldown_after_loss_minutes`（FR-RISK-1）の間。Executionのメモリ上の銘柄別ゲートであり、Risk Engineの判定とは別に働く（プロセス再起動で解除される）
- FR-ENTRY-6（見送りの扱い）: 上記ゲートによる拒否は、Policy → `paperexec`経路ではエラーではなく「見送り」として扱う。再試行しても同じ理由で拒否されるため、jev-traderジョブは失敗にせず、`paper entry skipped`としてログに残して正常終了する。ゲート以外のEntryエラーはジョブ失敗とする
- FR-ENTRY-7（入力検証）: `Enter`は発注前に、シグナル方向がLONG/SHORTであること、Risk Engine通過済み（`risk_passed`）であること、数量>0、価格が有限かつ>0、指値価格を指定する場合は有限かつ>0、指値注文では指値価格が指定されていることを検証し、違反は注文を作らずに拒否する。板価格の欠損（0）が約定・時価更新・決済価格にならないよう、`TryFillPending`・`OnSnapshot`・`Close`の価格も同様に検証する
- FR-ENTRY-8（約定モデル: 呼値・スプレッド・手数料・滑り・立会）: Paper Entry/Exitはシグナル価格（直近価格）での全量約定にせず、`internal/service/fillmodel`の約定モデルで価格・手数料を決める。Paper Trading（`execution`）とバックテスト（FR-BT-4）は同じモデル（`fillmodel.Costs`。値はSettingsの売買コスト設定。FR-COST-1）を使う
- FR-COST-1（売買コストの想定を設定にする、issue #779）: コストの前提（手数料・スリッページ・SHORTの貸株料）をコードに埋め込まず、Settingsの「売買コストの想定」（`runtime_settings`の`cost.*`。保存で再起動不要）に持つ。**Paperの約定・バックテスト・メタラベリングのラベル（EV）の3つが同じ設定を参照する**（`internal/config/costsettings`が唯一の定義）。
  - **設定項目と既定値（変更前の挙動と同じ）**: `cost.fee_bps`（約定代金に対する手数料、片道。既定0）、`cost.fee_fixed_jpy`（1約定あたりの定額手数料。既定0円）、スリッページ（板の最良気配／寄り・引けの気配値を超えて不利になる分）を売買方向（LONG/SHORT）×時間帯（ザラ場 `*_continuous_bps` ／ 寄り `*_opening_bps` ／ 引け `*_closing_bps`）で6項目（既定ザラ場2bps・寄り5bps・引け5bps。LONG/SHORTとも同値）、`cost.short_borrow_bps`（SHORTの貸株料。建玉の約定代金に対するbps、1建玉あたり。既定0）、`cost.reference_notional_jpy`（定額手数料を価格のリターン（bps）に換算するときの想定注文金額。注文サイズを持たないバックテストの%リターン・ラベル・感度表だけが使う。既定100万円）。スプレッドは板から別途モデル化されるため含まない（FR-ENTRY-8）。範囲は各0以上1000bps以下（定額手数料は10万円以下）
  - **反映先**: (1)Paper: 約定のたびにSettingsを読み、約定価格・手数料（`paper_orders.fees`・`slippage_bps`）とSHORTの貸株料（決済時の`realized_pnl`から控除）に反映する。設定が読めないときは`execution.Config.Fill`（既定は同じ値）で約定し、決済を止めない。(2)バックテスト: 実行ごとに同じ設定を読み、`Trade`の`NetReturnPct`（手数料・貸株料は`FeeReturnPct`、スリッページは`SlippageReturnPct`）に反映する。(3)ラベル: トリプルバリアのコスト想定（`barrier.cost_bps`、FR-CAL-4。既定10bps）に、約定モデルの往復コストの**既定値からの差**（手数料・定額手数料・スリッページ・貸株料の増減）を足した値を方向別に使う。既定のままでは差は0でラベルのコストは10bpsのまま変わらない。設定を変えると以降に付くラベルとそれから作るメタラベリングのEVが変わる（付与済みのラベルは書き換えない）。バリア設定または売買コスト設定の保存で、ラベルのコストが損切り幅以上になる組み合わせは拒否する
  - **警告**: Calibration画面の整合表（FR-CAL-4A）の`cost_mismatch`は、**barrierの基底コスト（`calibration.barrier_cost_bps`）が既定から外れている**ことを知らせる（手数料・スリッページを変えても出ない。ラベルのコストは手数料・スリッページの増減に追従するため、差は基底コストと既定の往復コストの差だけで決まる）。ラベルのコストにはスプレッド分の余裕を見込むため、その差が0〜15bps（基底コストが既定の往復コスト4bps以上かつ19bps以内）なら許容する（暫定）。手数料・スリッページの変更は、約定・バックテスト・ラベルが同じ設定を読むことで一致させ、警告の対象にしない
  - **SHORTの扱い（決定記録）**: SHORTは**信用取引の売建（制度信用を想定）**として扱う。モデルに入れるのは貸株料（`cost.short_borrow_bps`。建玉の約定代金に対するbps、既定0）で、決済時の損益に入る（バックテスト・ラベルにも同じ値が入る）。**入れないもの**: 逆日歩・金利（買方金利・貸株の金利）は日をまたぐ保有で発生する費用で、ポジションは日跨ぎをしない（引け前強制決済、FR-EXIT-1）ので対象外。信用取引の手数料体系は証券会社・口座で異なるため、手数料（`cost.fee_bps`/`cost.fee_fixed_jpy`）は売買方向で分けず共通とする。実際に使う証券会社・口座の手数料体系と貸株料は**要確認（運用者）**で、確認するまで手数料0・貸株料0の既定のまま動く（これは前提であって実績ではない）
  - **既定値の根拠**: 手数料0は「kabuステーション側の証券会社が国内株現物で手数料無料」という前提（要確認（運用者））。スリッページ2bps（ザラ場）・5bps（寄り・引け）は、板寄せの約定が最良気配からずれやすいことを見込んだ仮の値で、実測に基づくものではない
  - **見直し**: 見直し日は**Paperの約定が100件以上たまった日、またはそれまで3か月ごと**（初回の目安は2027-01-17）。基準: `paper_orders.slippage_bps`の分布（時間帯別（ザラ場・寄り・引け）の平均と95パーセンタイル）が想定（2bps／5bps）を上回る（平均が想定の1.5倍超、または95パーセンタイルが想定の3倍超）ときは想定を上げる。この分布は`tools/verify-queries.sql`のQ10（時間帯 open／regular／close × 売買方向の約定件数・平均・95パーセンタイル。生の分布だけを出し、想定や1.5倍・3倍との比較は運用者が出力と突き合わせて行う。`performance-evaluation.md`参照）で取る。手数料・貸株料は証券会社の条件が変わったとき、または実際の約定明細（記録項目: `paper_orders.fees`・`paper_orders.slippage_bps`、将来の実約定との差）と食い違うときに見直す。見直した日・理由・変更前後の値は運用者がPRまたは変更履歴に記録する
  - **コスト感度表**: 追加の往復コスト（既定0/2/5/10bps）を各取引のnetリターンから引いたときのExpectancyと、なお利益が残る取引の割合を出す。割合は2つあり、混同しない: `positive_share`は**実現した再生netから追加コストを引いて0超になった取引の割合**、`predicted_ev_positive_share`は**エントリー判断時のメタモデルの予測EV（bps）から追加コストを引いて0超になる取引の割合**（予測EVを持つ取引だけが分母で、その件数が`predicted_ev_trade_count`。旧エントリー則の取引は含まない）。`GET /performance/cost-sensitivity`（Performanceの条件と同じクエリ。`format=csv`（既定）／`json`）が、そのバックテストのForward取引（実行時の売買コスト設定込み）を再計算する（`internal/service/backtest/sensitivity`。予測EVは`backtest.Trade.PredictedEVBps`）。Performance画面のバックテストフォームの「Download cost sensitivity (CSV)」ボタンが、フォームの現在の入力値でこのCSVを開く
  - 呼値単位: 約定価格は東証の呼値の単位（標準テーブル。3,000円以下1円、5,000円以下5円、30,000円以下10円、50,000円以下50円、300,000円以下100円…。TOPIX100構成銘柄・ETF等の特例テーブルは扱わない）に載せ、注文に不利な側へ丸める（買いは切り上げ、売りは切り下げ）
  - スプレッド: ザラ場の成行は板を跨ぐ（買い＝最良売気配`ask`、売り＝最良買気配`bid`）。板が無い（`bid`/`ask`がNULLまたは逆転）場合は`spread_bps`の半分を直近価格の不利側へ乗せ、`spread_bps`も無ければ直近価格とする
  - 滑り: 板の気配に加えて不利側へ`SlippageBps`（初期値2bps）を乗せる。約定価格との差を`paper_orders.slippage_bps`（直近価格に対する不利方向のbps。呼値丸め・スプレッド込み）に記録する
  - 手数料: 約定代金の`FeeBps`（初期値0bps。kabuステーションAPIを提供する証券会社の国内現物手数料が無料のため）を`paper_orders.fees`（円）に記録し、`realized_pnl`はエントリー・Exit両約定の手数料を差し引いた値とする
  - 昼休み・立会時間外: 前場11:30〜後場12:30の昼休み、大引け後、非営業日は約定しない（`marketcalendar.PhaseClosed`）。Entryは`ErrOutsideTradingSession`、手動`Close`（`POST /positions/:id/close`は409）・Kill Switchの`CloseAll`も同様に約定せずポジションを保持する（`CloseAll`は`ErrOutsideTradingSession`を含むエラーを返し、次の立会で再度決済する）。`OnSnapshot`はExit条件が成立しても昼休み中はクローズせず、次の立会の足で再評価する。PENDING指値も昼休み中は約定せず次の立会まで待つ
  - 寄り・引けの気配: 前場・後場の寄り（9:00・12:30の最初の1分足）と大引けのクロージング・オークション（15:25〜15:30）は板寄せの単一価格約定として、ザラ場の1分足とは別に扱う。スプレッドは跨がず、直近価格（気配値）に`AuctionSlippageBps`（初期値5bps）の不利な滑りと呼値丸めを適用する（`marketcalendar.Calendar.PhaseAt`）
  - 指値: 板の気配が指値を満たす（買い＝`ask`≦指値、売り＝`bid`≧指値）ときに約定する。約定価格は気配＋滑り（呼値丸め後）だが、指値より不利にはならない
- FR-EXIT-1: 以下のExit条件を併用する: 固定Stop Loss、固定Take Profit、Trailing Stop、Jev方向反転、continuation_probability低下（しきい値はFR-EXIT-2）、VWAP逆クロス、最大保有時間到達、引け前強制決済（`force_flat_before_market_close_minutes` 分前から、大引け15:30 JSTを基準に判定する。前場終了11:30は対象外）。VWAP逆クロスは「価格がVWAPの不利側へ抜けた瞬間」（前回評価時は不利側でなく、今回評価で不利側）のみ成立し、不利側に滞在しているだけでは成立しない（不利側でエントリーしたポジションは、有利側へ抜けた後に再び不利側へ抜けるまでこの条件でクローズしない）。前回評価が無い最初の評価は、建値と現在VWAPの関係を前回の関係とみなす
- FR-EXIT-2: 初期値: `stop_loss_pct=0.6`, `take_profit_pct=1.2`, `trailing_stop_pct=0.5`, `max_holding_minutes=20`。continuation_probability低下（FR-EXIT-1）のしきい値は、上限`0.60`（`execution.Config.MinContinuationProbability`。FR-POLICY-1/2の既定のエントリーしきい値と同値）とポジション方向（LONG/SHORT）の現行エントリーしきい値`policy.{long,short}.min_continuation_probability`の小さい方（`min(0.60, エントリーしきい値)`）とする。エントリーしきい値は`config/strategy.yaml` < DB `runtime_settings`（Settings画面・自己改善、FR-POLICY-4、FR-SELFIMPROVE-5）の解決後の「評価時点で有効な値」であり、ポジションを開いた時点の値は保存・固定しない（Exit評価中にしきい値が変更された場合は、変更前または変更後のどちらか一方の値で評価する）。ポジション方向の値だけを使い、1回のExit評価（`EvaluateExit`）につき高々1回だけ読む（`continuation_probability`が上限`0.60`以上なら読まない）。評価結果はそのまま決済（`Close`）に使い、決済側でしきい値を読み直さない。エントリーしきい値を0.60未満へ下げても、そのしきい値でエントリーした直後の評価で即Exitしない（例: しきい値0.55でエントリーした判断`continuation_probability=0.57`はExitせず、0.55を下回るとExitする）。しきい値を0.60より厳しくしてもExitは0.60のまま、既定（0.60）では従来どおり0.60未満でExitする。エントリーしきい値の読み取りに失敗した場合は0.60で評価を続ける（FR-EXIT-3） これらの出口とトリプルバリアのラベル（FR-CAL-4）の基準は別の値で、既定のままでは一致しない。対応表・不一致の警告・ラベル対再生の比較・「(c)差を許容し検知する」とした決定の理由はFR-CAL-4A（`components-platform.md`）に従う。出口の既定値（SL0.6%/TP1.2%/トレーリング0.5%/20分）は、Paper取引の実績が無い間は変えない。
- FR-EXIT-3: Jev API不応答時も、既存ポジションはコードベースのExit Ruleで管理を継続する（Jev不応答を理由にリスク管理を停止しない）。同様に、PENDING指値の約定処理（`TryFillPending`）の失敗は、`OnSnapshot`による保有ポジションの時価更新・Exit評価を止めない（失敗はログに残し、当該注文のみ飛ばす。ポジションが既にあるため約定し得ないPENDING注文は`REJECTED`にする）
