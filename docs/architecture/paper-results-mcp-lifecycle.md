# Paper 実績 MCP の起動・停止・再起動（設計メモ）

issue #795。`docs/architecture/paper-results-mcp.md`（#783）の MCP を、Settings 画面の操作だけで起動・停止・再起動できるようにする。実装前に、安全条件との両立案を残す。方針は「悠太さんが手作業で行う設定・操作を残さず、すべて管理画面で行う」。

## 1. 決めたこと（issue #795 と悠太さんの追加要件）

- 起動・停止・再起動を Settings の外部連携カードから行う（#792 で「今回は実装しない」とした項目）。
- アプリの起動時、MCP が有効（`enabled=true`・API キーあり・待受アドレスが許可範囲）なら MCP も自動で起動する。無効・キー空・不正アドレスなら起動しない（既定オフは変えない）。画面には「次回起動時も自動で起動する」と表示する。
- アプリの終了時は MCP も止める。
- アプリが異常終了・kill されても MCP が孤児で残らない。
- Windows ログオン時のアプリ自動起動は**新しく作らない**。すでにある（インストーラーのスタートアップショートカット `--supervise`、既定ON。`requirements/non-functional.md` §3）。PC の再起動後は、この経路でアプリが立ち上がり、アプリの自動起動で MCP も復帰する。ホスト再起動後の無人復帰は Windows の自動ログオンが前提である。

## 2. 安全条件との両立案

| 安全条件 | 両立のさせ方 | 確認するテスト |
|----------|--------------|----------------|
| 1. MCP は別プロセス。読み取りの DB は `mode=ro` + `query_only`（設定ツールの書き込みだけが別の狭い接続で、MCP が自分で開く。`architecture/paper-results-mcp.md` §7.3）。アプリの書き込み権限・DB 接続を渡さない | アプリは `paper-results-mcp(.exe)` を `os/exec` の**子プロセス**として起動するだけ。DB は子が自分で開く（読み取りは `mode=ro`。`readdb` は変更しない。設定ツールの書き込み接続も子が自分で開き、アプリからは渡さない）。アプリの DB 接続・ファイルハンドル・`ExtraFiles` は渡さない（標準入出力以外のハンドルは継承しない）。子の標準入力は null、標準出力は捨てる。環境変数は許可リスト方式で渡す（`PATH`・OS の基本変数・`PITHA_DB_PATH`・`PITHA_RISK_PATH` だけ。アプリが持つそれ以外の環境変数は渡さない。許可リストが空に一致しても、アプリの環境全体は渡さない） | `proc` の環境・引数テスト、既存 MCP テスト（`readdb`・8 ツール・書き込みツールなし）をすべて通す |
| 2. 既定オフ、キー空なら待受しない、待受アドレス検証は現状どおり | 起動前の判定は `settings.Load` と `settings.ValidateListen`（MCP プロセスと同じ規則）で行い、満たさないときは**プロセスを作らない**。判定に通っても、プロセス自身が起動時に同じ検査を行う（二重の防御）。`settings`・`server.go` の検証は変えない | 自動起動の条件テスト（有効・キーあり・有効なアドレスだけ起動） |
| 3. API キーを起動引数・環境変数・ログ・画面・プロセス一覧に平文で出さない | 子の引数は `-config <設定ファイルのパス>` だけ（パスは秘密ではない）。キーは設定ファイル（`0600`）から子が自分で読む。アプリ側の起動管理は、キーが空かどうかを見るだけで値を保持しない。子の標準エラーは上限付きのバッファに受け、**終了理由の分類にだけ使う**（ログ・画面には分類した固定文だけを出し、子の出力そのものは出さない） | キーが引数・環境・ログ・画面・子の出力に出ないテスト |
| 4. 二重起動の防止。起動失敗・異常終了を状態表示に出す。画面に再起動ボタン | (a) 管理側で排他（起動・停止・再起動は一つずつ）。(b) 管理下の子が生きていれば起動しない。(c) 起動前に待受アドレスへ TCP 接続し、すでに応答があれば**起動しない**（アプリの外で起動された MCP・直前のアプリの残りを含む）。状態は 停止中／起動中／待受中／エラー（＋キー未設定）。異常終了は、操作者の停止でない子の終了として検知し、終了理由（固定文）を表示する。自動再起動のループは作らず、再起動は画面のボタンで行う | 二重起動しないテスト、起動失敗・異常終了の状態テスト |
| 5. 画面からの操作は認証済みのローカル操作のみ（CSRF 対策） | `POST /settings/mcp/start`・`/stop`・`/restart` は既存の `middleware.Session`（セッション Cookie `SameSite=Strict` ＋ CSRF トークン必須）・`HostGuard`・Setup Guard の下に置く。GET では何も起動しない。新しい認証機構は作らない | Cookie なし・CSRF なしは 403、Setup 未完了は閉じる、のテスト |

## 3. 構成

- 新パッケージ `internal/service/paperresultsmcp/proc`（`Manager`）。子プロセスの起動・停止・状態を持つ。`settings` だけに依存する（`readdb`・`query`・アプリのリポジトリには依存しない）。
- `internal/service/paperresultsmcp/admin` が `Manager` を持ち、`View`（状態表示）と `Start` / `Stop` / `Restart` / `AutoStart` / `Shutdown` を提供する。ハンドラ（`internal/web/handler/mcpsettings`）とパネル（`internal/web/organisms/mcp`）は `admin` だけを見る。
- `internal/bootstrap/mcpwire` が `admin.Service` を 1 つ作り（`New`）、`Start`（`AutoStart` を別 goroutine で）・`Stop`（`Shutdown`）・`RouterOptions`（Settings のカード）を提供する。`cmd/desktop`（`App.startup`/`App.shutdown`）と `cmd/server`（起動・終了経路）が同じ関数を呼ぶので、両方で同じ挙動になる。`internal/bootstrap` 本体（`Services`）には置かない: ディレクトリの行数上限（linterly）に余裕がなく、MCP の起動管理はアプリの背景サービス（Scheduler など）の起動・停止順序とも独立だからである。

## 4. 自動起動

`Services.Start` が成功したあと（Wails の `OnStartup`、`cmd/server` の起動経路）に `mcpwire.Start` が `AutoStart` を呼ぶ。`Services.Start` が失敗したときは呼ばない（失敗したアプリの後ろに MCP を残さない）。条件は `Start` と同じで、次をすべて満たすときだけ起動する。

1. 設定ファイルが読める（権限 `0600`、JSON が正しい）
2. `enabled=true`
3. `api_key` が空でない
4. `listen` が許可範囲（loopback と、この PC の tailnet アドレス）

満たさないときは起動せず、INFO ログに理由の分類だけを残す（既定オフは何も起こらない）。実行ファイルが無いときは WARN ログと「エラー」の状態にする。起動は画面の描画やアプリの起動を待たせない（別 goroutine。`Shutdown` で打ち切る）。

待受アドレスが tailnet アドレスで、その PC のインターフェースにまだ割り当てられていないとき（ログオン直後で Tailscale がまだ上がっていない）だけは、最大 90 秒（2 秒間隔）待ってから判定し直す。待つあいだはロックを持たず、アプリの終了で打ち切る。それでも付かなければ起動しない（それ以外の拒否は待たない）。

画面の状態表示は、この条件（と、`paper-results-mcp` の実行ファイルがアプリ本体のフォルダにあること）を満たすあいだ「次回起動時も自動で起動する」と出す。満たさないときは「自動では起動しません（理由）」と出す。

## 5. 終了時・異常終了時・孤児の防止

| 場面 | 動き |
|------|------|
| 通常終了（Wails の `OnShutdown`、`cmd/server` の SIGINT/SIGTERM と待受失敗。どちらも `Services.Stop` より前に `mcpwire.Stop`） | `Shutdown` が子を止め（Unix 系は SIGTERM、5 秒で kill。Windows は終了させる）、終了を待ち、以後の起動を拒否する。自動更新のインストーラーは `OnShutdown`（`mcpwire.Stop` と `Services.Stop`）のあとに起動するので、MCP の実行ファイルが使用中のまま置換されることはない |
| アプリが異常終了・kill された | **Windows**: 子を `CREATE_SUSPENDED` で作り、Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）に入れてから `NtResumeProcess` で動かす（ジョブに入る前には 1 命令も実行しないので、アプリがその間に消えても孤児は残らない）。ジョブのハンドルはアプリだけが持ち、アプリのプロセスが消えると OS がハンドルを閉じて子を終了させる。ハンドルは閉じない。ジョブの作成に失敗しても次の起動で再試行する。**Linux**: `Pdeathsig=SIGKILL`（親スレッドの終了で発火するため、起動と待機を専用のロック済みスレッドで行う）。その他の OS は異常終了への保護がない（本番は Windows）。入れられなかった場合は子を止めて起動失敗にする（孤児を作らない側に倒す） |
| `--supervise` によるアプリの再起動 | 監督プロセス（`internal/supervisor`）は子のアプリだけを見る。アプリが異常終了すると上の経路で MCP も消え、再起動した新しいアプリの `AutoStart` が MCP を起動する。旧 MCP がまだ消えきっていない場合に備え、`AutoStart` は待受アドレスが応答しなくなるまで最大 5 秒待ってから起動する。それでも応答するなら（アプリの外で起動された MCP）起動せず、二重起動しない |
| 操作者が終了コード 0 で終了（監督も終了） | 通常終了と同じ。MCP も止まる |

## 6. 状態

| 状態 | 条件 |
|------|------|
| 停止中 | 無効、または有効だが子が動いておらず待受もない（理由を併記） |
| キー未設定 | 有効だが `api_key` が空 |
| 起動中 | アプリが子を起動してから 10 秒以内で、まだ待受に接続できない |
| 待受中 | 待受アドレスへの TCP 接続が成功（アプリが起動した子か、アプリの外で起動されたものかを併記。後者は画面から停止できない） |
| エラー | 実行ファイルが無い・起動に失敗・異常終了（操作者の停止でない終了）・起動から 10 秒たっても待受しない。理由は固定文（ポート使用中・認証設定なし・設定ファイルを使えない・終了コード） |

設定ファイルが起動後に更新されている（保存・キー再生成）場合は「設定が変更されています。再起動すると反映されます」と出す（設定ファイルの更新時刻と起動時刻の比較。キーには触れない）。

## 7. 手作業として残るもの

- Grok Bot 側への URL と `Authorization` ヘッダーの登録（アプリの外）
- Tailscale / トンネルの設定（アプリの外。`paper-results-mcp.md` §4）
- ホスト再起動後の無人復帰に必要な Windows の自動ログオンの設定（アプリの外）
- 待受アドレスが tailnet アドレスのとき、Tailscale が 90 秒以内に上がらないと自動起動しない（その後の自動再試行はない。画面の「起動」か「再起動」、または Tailscale が上がってからのアプリ再起動で復帰する。loopback の既定では起きない）
- 設定の保存・API キーの再生成は、動いている MCP には「再起動」まで効かない（画面に「設定が保存されています…再起動で反映」と出す。無効化・キーの失効を即時にしたいときは「停止」または「再起動」を押す）
- インストーラー（`--supervise` のスタートアップ項目）を入れないと PC 再起動後の復帰は起きない（既定ON）

上記以外に、MCP を使うために行う操作（起動コマンド、タスクスケジューラへの登録、JSON の手書き）は残さない。
